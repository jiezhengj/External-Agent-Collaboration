# 外部代理持续协作 Skill：测试用例

> 2026-08-05 新增验收矩阵：50 个 `test_*.py` 已在本机通过，并在 GitHub Actions 的 macOS/Windows × Python 3.10/3.13 矩阵通过；新增真实 PreToolUse hook、200 次跨进程状态更新、workspace migration、Construction interrupted/resume、review-gate/stale checkpoint 用例。真实 Provider smoke 与 coverage threshold 仍按专题第 18 节单独记录，不能由 fake launcher 回归替代。

## 1. 测试范围

覆盖 Skill 发现、配置诊断、会话生命周期、路由、CLI 调用、自动文件修改、越界拦截、隐私与故障恢复。Claude Code 与规划中的 Antigravity CLI 均按 harness 独立测试；已配置且当前 fingerprint 已信任的本机 profile 可直接执行最小、无敏感的真实验证，其余用 fake launcher 完成。所有新增用例必须注明 macOS、Windows 的验证证据或不受影响理由。

## 2. 用例

|编号|场景与输入|期望结果|
|---|---|---|
|TC-01|从项目根目录启动 Codex，提出“继续与 provider A 协作处理品牌策略”|Skill 可发现；解析或提示选择对应 session。|
|TC-02|普通简单改写请求|Skill 不隐式触发，Codex 直接回答。|
|TC-03|新主题、未指定 provider 且缺少 routing|在健康 provider 间按持久化公平轮换选择，创建 registry 与 handoff；有 routing 时由 TC-94 至 TC-100 覆盖。|
|TC-04|同主题存在唯一 provider A session|调用命令带精确 `--resume <id>`，不得使用 `--continue`。|
|TC-05|同主题存在多个 session|停止并返回候选，不随机恢复。|
|TC-06|用户指定 provider B，存在 provider A session|新建或使用 provider B session，绝不复用 provider A ID。|
|TC-07|provider A profile 缺失|`doctor.py` 返回缺失项目名，不暴露或猜测凭证。|
|TC-08|CLI 返回合法 JSON 与新 session ID|原子更新 `sessions.json`，写入输出和审计记录。|
|TC-09|CLI 返回无效 JSON、任务失败或 outcome 失败|记录失败；不污染 registry；不跨 provider 重试。|
|TC-10|主 provider 认证、余额、端点或暂时服务不可用|只记录脱敏 failure kind 和 retry time；最多启动一次另一健康 provider；两个结果均记录。|
|TC-11|`execute` 修改允许目录中的 Markdown|快照、修改清单、diff 和输出记录齐全。|
|TC-12|`execute` 试图写 `.env` 或 `secrets/`|脚本拒绝，目标文件不变。|
|TC-13|`execute` 试图执行 `git push`/`git reset`|命令策略拒绝，日志标记禁止行为。|
|TC-14|修改范围超出 handoff 的允许目录|后置 diff 检查标记 `needs_review`，不报告成功。|
|TC-15|交接包含 token、私钥或客户导出|预检拒绝创建调用并提示移除敏感内容。|
|TC-16|高风险代码改动完成|Codex 检查完整 diff 并运行项目规定的验证命令。|
|TC-17|一个 session 由 provider A 长期恢复|配置目录、topic 与 provider 始终一致。|
|TC-18|同一主题改模型配置或工作目录|拒绝恢复原 session，要求新建或 fork。|
|TC-19|首次需要新建文件、能力档案不存在|运行 ephemeral capability probe，并记录原生 Write 是否实际创建成功。|
|TC-20|能力档案未过期且 CLI/profile 未变|跳过 probe，不产生额外 provider 调用。|
|TC-21|模型报告缺少 Write 工具|立即运行 probe；若原生 Write 不可用，使用最小 Bash 白名单创建并更新档案。|
|TC-22|旧 session 的 initial_toolset 不含 Write，但 provider 新会话支持 Write|不把 provider 结果套用给旧 session；使用精确 Bash 兜底或显式 fork/new session。|
|TC-23|execute 未传 expected outcomes|在调用 provider 前拒绝请求。|
|TC-24|外部模型返回成功但文件内容不符合 `file_equals`|执行器返回 failed 并恢复本次任务变更。|
|TC-25|`command_succeeds` 未列入 validation allowlist|拒绝 outcome；不执行该命令。|
|TC-26|复杂代码执行、实时天气、PPTX、token、简单改写|分类分别为 external、native、native、prohibited、direct。|
|TC-27|任意外部可委派的新主题|健康 provider 严格交替，输出对应的 `starter_policy_*_rotation`。|
|TC-28|同类任务两家均有人工质量分结果|仍按公平轮换；指标只供审计和未来明确启用的学习策略使用。|
|TC-29|从 active session 运行 `--fork-session`|真实 CLI 返回新 ID；父子 session 均登记且父 session 不被覆盖。|
|TC-30|execute outcome 指向不存在文件且恢复 session 缺 Write|能力档案有效时自动 fork；探测失效时先探测再执行。|
|TC-31|归档 active session|session/topic 索引状态更新，生成非敏感 archive handoff。|
|TC-32|execute 新增符号链接或未声明二进制文件|清单检测并恢复，状态不得为 completed。|
|TC-33|execute 删除允许目录中的旧文件但未传 `--allow-delete`|检测、恢复并标记 needs_review。|
|TC-34|项目快照超过 500 MiB|调用前拒绝，要求缩小工作目录或执行范围。|
|TC-35|completed 高风险 execute|`review_execution.py` 只调用另一 provider 一次做 read-only critique，不回调执行者。|

|TC-36|外部 provider 返回超过 compact 上限|完整 result 仅落本地 runtime；Codex 只接收不超过 8 KiB 的 compact envelope、截断标记与路径。|
|TC-37|外部结果不符合受限 response schema|记录 `result_contract_failed`；仅剥离严格最外层 JSON fence 后可恢复为 structured；不以模型文本替代 outcomes，也不自动重复同一 consult。|
|TC-38|长持续主题完成多轮后恢复|只读取短 topic 状态、决策与本机 session 映射；不加载完整 transcript；topic state 不超过一页。|
|TC-39|大量非敏感文本的 batch dry-run|生成 manifest、样本 batch 和 JSONL schema；未达抽样质量阈值不得扩展全量。|
|TC-40|batch 中断后恢复|source hash 与 schema version 未变化的记录不重复处理；失败清单可独立重试。|
|TC-41|超出 execute 快照上限的大材料任务|拒绝单次 execute，建议只读 batch 或拆分为小范围写入批次。|
|TC-42|高风险 batch 出现异常或抽样不一致|只对异常/样本触发一次独立审查，不让第二 provider 重读全部材料。|
|TC-43|新增实质优化需求|存在对应专题入口（含讨论基线、实施状态和证据）、DEC 记录、受影响主文档更新、迭代记录和验证证据；无重复完整文档版本或孤立顶层专题文件。|
|TC-44|全局可发现时提出“审查整个仓库的鉴权实现”或“实现这个模块及所有关联调用”|`SKILL.md` 元数据作为 Skill 发现信号而被选中；随后才运行分类、配置检查和路由。|
|TC-45|全局可发现时提出普通问答、常规评审或小型单文件修改|`SKILL.md` 元数据不应选中本 Skill；Codex 直接处理。|
|TC-46|Skill 已被选中但本地 provider 配置不可用|不得发起外部 CLI 调用；返回或记录明确的本地配置诊断，不能猜测 provider 或凭证。|
|TC-47|活跃 session 的 provider 正处于 health 冷却|不迁移该 session；自动调用使用另一健康 provider 的新 session，并记录 source session key。|
|TC-48|余额/认证/端点故障、限流/传输/服务端故障|分别写入 24 小时、5 分钟至 6 小时的脱敏冷却；无后台探测。|
|TC-49|profile 含 `ANTHROPIC_MODEL` 与 FABLE/OPUS/SONNET/HAIKU/SUBAGENT 环境映射|runner 注入环境但命令不含 `--model`，不干预 provider 内部模型或子代理。|
|TC-50|profile 无当前 fingerprint 的本地 trust record，或 endpoint/模型映射/config dir/非密钥 environment 发生变化|runner 在启动 Claude Code 前拒绝；已授权实施自动刷新 record 后才可调用。|
|TC-51|`dontAsk` 返回 `permission_denials`|状态为 `blocked_by_permission`，不等待不可操作的终端审批，也不得报告 completed。|
|TC-52|Windows 上执行 `command_succeeds`|使用与 `--validation-argv` 相同的 JSON 参数数组、`shell=False` 执行并返回 0；不依赖 `true` 等 Unix 命令。|
|TC-53|Windows 与 macOS 各有平台 local profile|各自读取对应的直接 `auth_token`、launcher 和 `config_dir`；不得要求环境变量、Keychain 或 Credential Manager。|
|TC-54|Windows 读取 macOS session/capability 记录|不得匹配或恢复该 session；旧能力记录视为过期；迁移 dry-run 报告 foreign record。|
|TC-55|同一份 `providers.shared.json` 在模拟 Windows 与 macOS 主目录加载|`config_dir_relative_to_home` 分别解析到各自主目录；逻辑 `claude` launcher 保持由 PATH 解析。|
|TC-56|版本化 shared profile 含 `auth_token`、绝对目录或 `.exe` launcher|加载器在外发前拒绝；直接 token 只能出现在 Git 忽略的平台 local profile。|
|TC-57|legacy profile 含直接 token，运行当前平台迁移|token 复制到当前平台 Git 忽略的 local profile；shared 不含 token；两端平台 profile 未就绪时拒绝清理 legacy。|
|TC-57a|旧 session 缺 Write 且当前主机未确认 POSIX shell|不得生成 `touch`/`mkdir -p`；要求 native Write、fork 或新 session。|
|TC-58|Claude Code 返回 `--json-schema` 的 `structured_output`|runner 优先读取该字段，生成符合统一 response contract 的 envelope；不得依赖模型在 `result` 中裸输出 JSON。|
|TC-59|Claude Code 的 result 在 JSON 前后含说明，或 handoff 要求与 runner contract 冲突|记录明确的 contract failure/compatibility fallback；不把无效文本当 schema 成功，也不自动重复同一调用。|
|TC-60|Claude Code profile 启用插件/skills/MCP，默认 invocation 与 opt-in `--bare` invocation 对比|默认不得意外跳过隔离 profile 能力；仅通过显式、已验证的 bare profile 才可进入 bare；两端结果分别记录。|
|TC-61|Claude stream JSON 出现 API retry、plugin/MCP load failure 或 nested subagent event|仅记录允许的脱敏状态/计数和终态；不落完整事件流、子代理文本、prompt 或凭据。|
|TC-62|session record 从旧 schema 迁移到 `harness=claude_code`|保留现有 Claude session；迁移不得猜测或写入 Antigravity conversation ID。|
|TC-63|Claude Code session ID 传给 Antigravity，或 Antigravity conversation ID 传给 Claude Code|跨 harness 恢复在调用前拒绝；不产生 provider 请求。|
|TC-64|Antigravity fake CLI 对 `agy -p --output-format json --json-schema` 返回 `SUCCESS` 和 `structured_output`|adapter 归一化 session/conversation ID、状态、usage 和 structured result；profile 内 model/effort/agent 不由分类器临时覆盖。|
|TC-65|Antigravity headless 的工具请求被软拒绝但进程退出 0|检测 stderr/status/stream permission 事件，返回 `blocked_by_permission`，不得报告 completed。|
|TC-66|Antigravity 缺少交互式认证、unknown model、schema error、timeout|无凭据诊断分别明确；只有已归类 availability failure 才允许预先许可的一次替代，不把配置或 contract 错误误路由。|
|TC-67|Antigravity execute 尝试使用 `--dangerously-skip-permissions`|主工作树 runner 在 CLI 启动前拒绝；仅 trusted `local-full-auto` isolated executor 可传该 flag。|
|TC-67a|AGY `local-full-auto` profile|仅显式启用、当前 fingerprint 已信任、经 isolated executor 且声明唯一目标/outcome 时 argv 才允许 `--dangerously-skip-permissions`。|
|TC-67aa|AGY full-auto 指向主工作树|启动前拒绝；只能经 disposable isolated executor 运行。|
|TC-67ab|main-worktree full-auto policy unit test|`dangerously_skip_permissions=true` 必须命中 isolation guard；false/缺失不得误判。|
|TC-67b|同一 P3 smoke 无 flag / dangerous 对照|无 flag 记录软拒绝；dangerous 成功才可解锁 execute，若目标仍不匹配则保留无内容工具/权限诊断并固定 AGY 为只读。|
|TC-67d|Windows disposable isolated full-auto 对照|以 Git 忽略且初始为 `P3 pending` 的 fresh source 运行；当前预期目标不匹配、`tool_diagnostics.permission_mode=always-proceed`、`write_tool_available=true`、无非目标变更。该失败只补齐跨平台证据，不改变 AGY 只读路由。|
|TC-67c|Claude execute 编排|纯编辑使用 `acceptEdits`；已知命令只传精确 `allowedTools`。|
|TC-68|公共 `route_harness.py` 的新主题路由|仅无历史、无敏感、明确独立审查且当前 read-only profile/launcher/trust 就绪时选择 Antigravity；否则保持 Claude Code，Claude Code 内的 DeepSeek/MiMo routing policy 不被 harness router 改写。|
|TC-69|同一 harness/profile 的 trust、health、capability record 在 macOS 与 Windows 间读取|key 中包含 harness/profile/platform；不同平台或不同 harness 一律失效，不共享 session、health 或 capability。|
|TC-70|每个新增 CLI adapter 的测试矩阵|macOS 与 Windows 均覆盖 launcher discovery、路径、JSON/schema、permission denial、timeout、fake CLI；已配置、已信任的本机 profile 直接运行最小真实 smoke，不以逐次对话授权替代工程验收。|
|TC-71|架构 handoff 仅描述“不得发送 token/secret/credential”，不含值、配置正文或私有数据|分类器不得仅按敏感词误判为 `prohibited`；保留正常的 direct/external 决策，并继续拦截真实凭据形态。|
|TC-72|包含真实 API key/Bearer 值、私钥块、`.env` 正文或客户导出的 handoff|高置信度 `prohibited`；最终 handoff scanner 同样阻断，输出不回显秘密。|
|TC-73|存在 Claude Code active session 的后续主题|无论 Antigravity 是否已启用，恢复原 Claude session；不得迁移到独立 reviewer role。|
|TC-74|无历史会话的新项目 execute、需要 CC Switch plugin/MCP、或普通项目协作|选择 Claude Code project-collaborator role；DeepSeek/MiMo 按 routing policy 选择，缺少配置时公平轮换。|
|TC-75|无历史会话、只读且请求独立审查/第二方案/反方意见/风险清单|`route_harness.py` 自动选择 ready Antigravity independent-reviewer role，输出 `routing.basis=explicit_independent_review`；未就绪时不启动它，明确报告未就绪并交回 Codex，绝不静默改送 Claude Code。|
|TC-76|高风险 Claude Code execute 完成并需要独立验证|Claude Code 保持执行者；Antigravity 最多启动一次只读 critique，不竞争执行或自动回调。|
|TC-77|legacy Claude session/trust/health/capability/metric record 运行 `migrate_harness_state.py`|默认 dry-run 仅报告；`--apply` 先备份再写入 `claude_code` harness/profile/platform identity，保留旧 Claude session ID。|
|TC-78|启用 `EXTERNAL_AGENT_HARNESS_STATE=1` 时，同主题仅存在 foreign-harness active session|Claude Code 在路由前 fail-closed；关闭 flag 后保持当前 Claude-only 路由行为，且不迁移 foreign session。|
|TC-79|Antigravity fake launcher 使用 read-only profile 调用|argv 包含 `-p --output-format json --json-schema --mode plan` 与精确 `--conversation`；绝不含 `--dangerously-skip-permissions`；解析 `SUCCESS` 的 `structured_output`。|
|TC-80|精确短语 smoke 使用 `--response-contract none --expected-response`|仅允许 ephemeral 的 `consult`/`critique`，不传 JSON schema；结果按去除首尾空白后的单行文本精确匹配。期望不一致必须 failed，且不得触发 provider failover；macOS 与 Windows 均保留默认 JSON contract 的独立回归。|
|TC-81|Antigravity profile 含 credential 字段、未 trust、`accept-edits` mode、或 soft permission denial|配置/信任在启动前拒绝；read-only adapter 拒绝非 `plan`；即使 exit 0 也映射 `blocked_by_permission`，不得记录 completed。|
|TC-82|`route_harness.py` 新主题、无敏感、明确独立审查，且 `antigravity_readonly` profile ready|自动调用 Antigravity；record 的 `harness=antigravity`、`routing.basis=explicit_independent_review`，标准 structured contract 有效且无项目文件改动；macOS 与 Windows 真实 smoke 均通过。|
|TC-83|P4 请求独立审查但 Antigravity profile/trust/launcher 未就绪，或请求 `execute`、`draft`、commands/outcomes/fork/non-standard contract|明确拒绝或交回 Codex；不得静默改投 Claude Code，不得调用 AGY execute、跨 harness 重试或修改项目文件。|
|TC-84|Goal 含 3 个 required criteria，只有 2 个 Run evidence 通过|Goal 保持 `active`；不得因最近一轮 Run 为 `completed` 而标记 `achieved`。|
|TC-85|Goal 的所有机器 criteria 通过，但 required independent review 或 user acceptance 缺失|Goal 保持 `active`；缺失的 review/acceptance 不能默认为通过。|
|TC-86|一次 Run 为 `completed`，但同一 Goal 仍有上一轮 criterion 失败且未重跑|Run 为 `completed`，Goal 仍为 `active`；聚合器必须按 criterion ID 汇总，而不是只读最后一轮总状态。|
|TC-87|Goal 的下一步依赖人工权限，且没有安全替代路径|Goal 为 `blocked`；记录 blocker、责任方、解除条件和证据，不报告 `achieved`。|
|TC-88|Goal 达到重试上限但必需 criterion 未通过|Goal 必须为 `failed`，不能报告成功；必须记录上限和未通过条件。|
|TC-89|用户明确取消 active Goal|Goal 为 `cancelled`，记录取消来源和时间；不得继续自动调用。|
|TC-90|Goal 要求 macOS 与 Windows 验证，仅 macOS 通过|Goal 保持 `active`；Windows 不能用 macOS 结果替代。|
|TC-91|平台条件标记 `not_applicable` 但没有理由或 evidence|拒绝关闭 Goal；`not_applicable` 必须附理由与验证证据。|
|TC-92|topic state 的 `State: completed` 被当作 Goal 结果|判定为不合法；topic state 只能提供持久化说明，不能替代 Goal contract 聚合。|
|TC-93|同一 Goal contract 与同一组 Run evidence 在 macOS 和 Windows 聚合|两端得到相同 Goal 状态和 criterion 结果；路径、命令和平台字段按各自平台解析，不共享 session/capability。|
|TC-94|配置缺少顶层 `routing`|自动使用 `fair_round_robin`，行为与旧 `round_robin_cursor` 兼容。|
|TC-95|`routing.default.strategy=fixed` 且目标 provider ready|新主题固定选择目标 provider；route metadata 为 `configured_fixed`。|
|TC-96|`weighted_round_robin` 权重为 `deepseek:2,mimo:1`|确定性 smooth weighted 序列长期按 2:1；不使用随机数。|
|TC-97|routing schema、策略、权重或 provider 引用非法|provider 调用前 fail-closed，返回 `routing_config_invalid`/`routing_provider_unknown` 等本地诊断，不自动换策略。|
|TC-98|shared、通用 local 与 macOS/Windows local 同时提供 routing|按规定顺序深合并；两端 platform overlay 独立生效，routing 不进入 provider trust fingerprint。|
|TC-99|`provider-metrics.json.routing_state` 损坏|保留 events，重建当前策略状态并继续确定性选择；不把状态损坏记为 provider availability failure。|
|TC-100|显式 provider、exact session、fixed/weighted policy 同时存在|显式 session/provider 优先；policy 只作用于无覆盖的新主题。|
