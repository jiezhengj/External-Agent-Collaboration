# 专题方案：外部代理协作效能优化

> 本方案属于[协作效能优化专题](README.md)。讨论基线、实施状态、主文档映射和后续证据以专题入口为准；这里不单独代表项目当前已实现状态。

## 1. 问题与目标

本方案优化的不是某一项孤立指标，而是在明确安全边界和验收质量不下降的前提下，让 Codex、外部协作者和本地工具各自处理最合适的工作。

衡量一次协作是否有效，采用以下整体目标：

> 用尽可能少的重复阅读、重复推理和无效往返，产出可验证的正确结果，并让 Codex 只承担必须由 Codex 承担的判断、原生工具操作和最终责任。

因此，token、费用、完成时间和模型数量都只是约束或观察值；不能为了降低任一数字而牺牲验收通过率、可解释性、安全或用户采纳。

不适用范围保持不变：敏感资料、密钥、客户导出、当前网页事实、已登录连接器数据、部署、破坏性操作，以及必须由 Codex 原生工具生成的图片、演示、表格、PDF 或最终格式化办公文件。

## 2. 统一决策模型

每个任务在调用前形成一份 `work_plan`。它不是额外文档负担，而是由分类器、文件清单和用户请求生成的短结构化记录：

```json
{
  "task_type": "code | document | research | creative | planning | data",
  "risk": "low | medium | high | prohibited",
  "source_scale": {"files": 0, "bytes": 0, "estimated_tokens": 0},
  "output_shape": "direct_answer | patch | structured_records | native_artifact",
  "verification": "none | schema | test | sample | source_check",
  "delegation": "direct | native_codex | external | batch",
  "return_mode": "compact | structured | file_only | debug",
  "review_policy": "none | sample | exception | independent",
  "stop_rule": "..."
}
```

选择路径时按以下顺序判断：

在此决策链之前，全球可发现的 Skill 先由 `SKILL.md` metadata 发现：恢复主题、独立/第二模型评审、全仓/关联模块/多文件任务和边界明确的独立实施是选中信号；简单问答、常规评审和小型单文件修改不选中。选中不等于调用，以下规则和 provider 配置检查才决定是否实际委派。

1. **安全与工具边界**：禁止或必须原生的任务不外包。
2. **验收形态**：不能说明如何验证结果的任务，先澄清或小样本试做，不启动大规模协作。
3. **信息压缩价值**：只有外部协作者可消化大量本地材料、且能将 Codex 最终必读内容压缩为很小的索引、异常或变更集时，才委派。
4. **独立视角价值**：只有存在实质不确定性、风险或候选差异时，才引入第二协作者。
5. **成本与时延**：在满足以上条件后，才用本地质量、完成率、耗时和费用指标选择 provider 与批量大小。

这使 token 控制、质量控制和效率控制成为同一条决策链：没有可验证的压缩，就没有大规模委派；没有质量风险，就没有第二次完整阅读。

## 3. 三层执行架构

```text
Codex：任务定义、原生工具、验收、例外决策、最终责任
  ↓ 短 handoff / work_plan
外部协作者：本地材料阅读、受限推理或实施、结构化落盘
  ↓ 索引、统计、异常、变更与证据路径
Codex：按需抽样、处理例外、必要时触发一次独立审查
```

### 3.1 Codex 的职责

- 理解用户目标、约束和风险；
- 选择 direct、native、external 或 batch；
- 生成最小 handoff、outcomes 和 stop rule；
- 运行原生工具、检查验收结果、处理异常；
- 只按需读取外部完整输出，不自动重读全部材料；
- 面向用户整合结论并承担最终责任。

### 3.2 外部协作者的职责

- 直接在工作区读取授权范围内的本地材料；
- 在持续 session 中积累与主题有关的理解；
- 在受控路径内写结构化中间结果、补丁或候选；
- 用规定 schema 报告结论、证据位置、失败和不确定性；
- 不替代 Codex 的实时检索、账户连接、富媒体生产或最终责任。

### 3.3 回传原则

默认回传的不是原文和完整推理，而是：run ID、状态、outcomes、变更路径、统计、风险、异常路径和固定长度摘要。完整 provider JSON 与长结果保存在本地 ignored output，只有在失败、抽样、调试或用户明确要求时才按范围读取。

## 4. 最小协作持久化

双 Agent 协作需要共享可恢复的接口，但不需要同步彼此的完整聊天、内部 session 和记忆。持久化的目标是减少重复理解和错误交接，而不是在用户项目中复制第二套知识库。

```text
项目真实产物
  源码、文档、数据、测试、Git 历史
  = 业务与实现事实的唯一来源

.ai-collaboration/
  project-context.md        稳定背景（少改）
  decisions.md              已确认且不能从产物推导的决策
  topics/<topic>.md         活跃主题的短交接状态
  sessions.local.json       本机 provider/session 映射
  runtime/                  可删除的 handoff、输出、日志、快照
```

### 4.1 持久化准则

写入协作层之前先问：另一位 Agent 能否仅凭项目文件、Git、测试结果和简短交接重新得出该信息？

- 能：不复制内容，只记录项目路径或证据链接。
- 不能、且会影响后续决策：写入 `decisions.md`。
- 仅与正在推进的主题有关：写入 `topics/<topic>.md`。
- 仅用于精确恢复 provider session：写入本地 ignored 的 `sessions.local.json`。
- 仅用于调试、失败恢复或审计：写入 runtime，并设保留期。

这项准则同时控制 token 与质量：不复制原文和完整 transcript，减少 Codex/外部协作者重复读取；保留关键决策、主题状态和 session 绑定，减少错误恢复、假设漂移和无效往返。

### 4.2 活跃主题的最小状态

每个 `topics/<topic>.md` 不超过一页，只有：目标、范围路径、已确认决策引用、当前状态、下一步、证据/产物路径和 stop rule。不得保存完整 prompt、模型推理、逐轮聊天或重复的项目摘要。

示例：

```markdown
# Topic: batch-document-index

- Goal: 为 `input/` 生成结构化索引。
- Scope: `input/`, `output/index.jsonl`, `docs/schema.md`
- Decisions: `decisions.md#batch-index-v1`
- State: schema 与两个样本批次已完成；编码异常待处理。
- Next: 修复编码处理后继续 batch 3。
- Evidence: `output/summary.json`, `tests/test_indexer.py`
- Stop rule: 样本质量和完成率达到已定义阈值。
```

### 4.3 runtime 不是长期记忆

`handoffs/`、`outputs/`、`logs/`、`snapshots/`、完整 CLI JSON 和 capability 实验属于运行缓存。默认不参与下次 handoff，不自动读入 Codex 上下文，并按 7–30 天或磁盘配额清理。只有任务失败、抽样复核、审计、调试或用户明确要求时，才按路径和范围读取。

主题完成时，将最终决策、产物链接和未决风险压缩到 `decisions.md` 或一份归档摘要，然后删除活跃 topic 文件；session 标记 archived 即可，无需保存 transcript。

## 5. 通用控制机制

### 4.1 结构化输出与紧凑回传

`collaborate.py` 增加 `return_mode`：

|模式|适用任务|返回给 Codex|完整内容位置|
|---|---|---|---|
|`compact`（默认）|大多数 consult/execute|run ID、状态、outcomes、变更、风险、最多 8 KiB 摘要|本地 output。|
|`structured`|提取、分类、规划|受 schema 与字段长度限制的 JSON|本地 output。|
|`file_only`|批处理 worker|状态、hash、索引路径|JSONL / batch result。|
|`debug`|故障排查|完整 CLI result|本地 output，且只由显式请求开启。|

外部最终答复也采用长度受限 schema：摘要、变更文件、运行命令、验证结果、风险和输出索引。模型输出不合约时记录错误，但不替代 outcomes 对结果的判定。

### 4.2 最小上下文与持续上下文

- handoff 只含本轮目标、相关路径、确认决策和验收要求；禁止复制完整对话或项目全文。
- 持续 session 只服务同一主题、provider、profile 和工作目录；每轮传递 delta。
- 长主题定期将已确认结论、未决项和产物索引压缩到本地状态文件；新 session 从该摘要恢复，不从完整 transcript 恢复。
- 若外部协作者需要的材料在磁盘可读，Codex 只传路径与读取目标，不传文件内容。

### 4.3 风险驱动的复核

独立复核不是默认双份工作，而是分级策略：

- 低风险：outcomes 与本地验证通过即可；
- 中风险：Codex 检查变更、测试和少量抽样；
- 高风险：只对关键变更、失败、低置信度或冲突样本触发另一 provider 的一次只读审查；
- 审查结论不自动回传执行者，不形成辩论循环。后续修改必须是新的明确步骤。

### 4.4 停止规则

每个 external/batch 任务必须至少有一个停止条件，例如：所有 outcomes 通过；已处理清单中的成功率达到阈值且异常已输出；抽样质量合格；达到预算/重试上限；发现敏感或不可验证材料。

达到停止条件后不因“可能还能更好”继续自动调用。

## 6. 按工况的优化策略

|工况|最优协作形态|质量与效率收益|必须的限制|
|---|---|---|---|
|简单问答、短改写、小范围修改|Codex direct|避免固定交接和启动成本。|不为取得一致意见外包。|
|实时事实、连接器、富媒体成品|Codex native|使用正确的实时数据和原生能力。|外部协作者不替代此路径。|
|多文件代码修复|外部 execute + Codex 验收|协作者读取关联模块并实施；Codex 聚焦 tests/outcomes/diff。|最小 allow path、tests、compact 回传；高风险只审关键变更。|
|大型代码库理解或排障|外部 consult / module index|将源码阅读压缩为模块图、依赖、假设和证据路径。|Codex 只打开关键文件；不要每轮重读仓库。|
|大量本地文本、数据或记录|batch + 本地 reducer|将大量材料压缩为结构化记录、统计和异常清单。|分片、schema、hash、断点、抽样；禁止逐篇全文回传。|
|长持续项目|持续 session + state summary|减少重新解释历史与重复探索。|主题隔离、delta handoff、定期摘要与归档。|
|架构、迁移、复杂规划|有限候选 + Codex 比较|获得独立路径和失败模式，而非单一路径依赖。|候选数量/长度受限；不自动多轮辩论。|
|创作与文案|有限候选落盘|扩大候选空间。|用户或 Codex 选择；不让所有草稿回流。|
|高风险代码、事实或安全边界|execute/analysis + exception review|用独立视角发现遗漏与边界问题。|第二协作者只审风险点、变更集和样本。|

## 7. 大批材料协议

### 6.1 适用与拒绝条件

仅当材料非敏感、每项可产生结构化小结果、可定义抽样或 schema 验收，并且 Codex 不需要逐字阅读全部原文时，才使用 batch。

如果每一份原文都必须由 Codex 人工裁定，或任务没有可验证输出，batch 不会产生有效压缩，应改为 direct/native、缩小范围或先试验小样本。

### 6.2 协议

```text
manifest + 小样本校准
  → 有界 batch worker
  → JSONL 结果与本地 reducer
  → 异常优先 + 随机抽样复核
  → 最终索引与结论
```

1. **manifest**：只记录路径、大小、hash、类型、分片 ID 和敏感标记；先选小样本验证 schema 与提示词。
2. **worker**：按文件数、字节数和估计 token 三个上限分片；每批仅读自身 manifest，输出 `batch-<id>.jsonl`。
3. **result**：每行包含源 hash、schema version、status、短结论、证据位置、置信度和错误码；不写长原文摘要。
4. **reducer**：本地聚合完成量、失败、字段完整率、重复 hash、异常与抽样候选，写 `index.json`、`summary.json`。
5. **复核**：Codex 默认只看 summary、异常和随机样本；不合格时停止全量扩展，先修正规则。

结果键为 `source_relative_path + source_hash + schema_version`，因此中断重启、provider 更换或重复运行都不会无意义重读未变化材料。

### 6.3 10,000 × 1 MB 示例

约 10 GB 的输入不能单次 `execute`：现有全项目快照上限会拒绝此类任务。正确路径是只读 batch：先小样本，后分片 worker，结果落 JSONL，reducer 生成统计与异常索引；若需要写回，则把写操作拆为小范围、可快照、可回滚的 execute 批次。

## 8. 路由、预算与 provider 选择

分类器扩展以下字段：

```json
{
  "estimated_input_bytes": 0,
  "estimated_return_bytes": 0,
  "return_ratio": 0.0,
  "batchable": false,
  "recommended_return_mode": "compact",
  "review_policy": "none",
  "token_policy": "direct | delegate | batch | native | reject"
}
```

路由规则：

1. 先执行安全、原生工具和验收形态判断。
2. 输入小或预计回传比高时，direct 或要求缩小任务；建议回传比阈值初始为 0.2，并用本地数据校准。
3. 输入大、可结构化验收且回传比低时，选择 external/batch。
4. 超过 execute 快照上限的任务不能单次 execute。
5. 同等可行 provider 再按同类任务的质量、完成率、返工、耗时和实际成本选择；样本不足时平衡探索，不按厂商宣称硬编码能力。
6. 第二审查只在高风险、outcome 异常、低置信度、抽样不一致或用户明确要求时启动。

预算控制首先限制 handoff、批次、返回、重试和复核范围；provider token/费用作为真实运行指标，而不是唯一的预设硬阈值。

## 9. 观测与验收

新增 `collaboration-efficiency-metrics.json`，仅记录：run ID、task type、action、文件数、输入字节估算、handoff 字节、外部 result 字节、回传 Codex 字节、return mode、batch 状态、外部 usage/cost（可获得时）、outcomes、抽样、人工质量、返工、采纳和耗时。不得记录原文、prompt、密钥或业务结论。

采用成对对照验证，而不是只看单次体验：对同类真实任务分别运行 Codex-only 与协作路径，并固定验收标准、时间窗口和风险等级。

|验收维度|通过条件|
|---|---|
|正确性|outcomes、测试、source check 与抽样不低于 Codex-only 基线。|
|Codex 上下文|compact/batch 场景下，返回给 Codex 的字节数相较完整 result 降低至少 90%。|
|总成本|外部 token/费用增加必须能由减少的 Codex 工作、返工或完成时间解释；否则缩小委派。|
|效率|批处理可断点恢复，未变化 source hash 不重复处理。|
|可审计性|每项结论能定位 source hash、输出记录和验证证据。|
|安全|敏感资料与本地凭证从不进入外部 handoff 或公开 metrics。|

## 10. 实施顺序

### P0：建立紧凑且可验证的回传

1. 实现 `return_mode`、长度受限 response schema 与 compact envelope。
2. 将完整 CLI JSON 保存在 ignored output，默认不打印给 Codex。
3. 记录 handoff/result/回传字节数；增加截断、schema 失败和按需读取测试。
4. 为持续 session 增加状态摘要和 delta handoff 模板。

### P1：按质量建设 batch

1. 实现 manifest scanner、小样本 dry-run、分片计划和 JSONL schema。
2. 实现 reducer、hash 幂等、失败清单、断点恢复与随机抽样。
3. 增加只读 `document_batch` action；明确拒绝大范围单次 execute。
4. 让 batch worker 使用 `file_only`/`structured` 返回，禁止逐项全文输出。

### P2：按实际效能路由

1. 扩展 task classifier、provider metrics 和效率指标。
2. 实现回传比、批量建议、预算/重试/审查策略。
3. 用非敏感小规模真实任务校准批次与抽样阈值。
4. 运行 Codex-only 与协作路径对照，按质量、返工、总成本和时间决定扩大范围。

### P3：长期维护

1. 根据验证后的质量和采纳数据更新路由，而不是只追求最低 token。
2. 建立按路径、段落和证据的按需检索，避免完整文件回读。
3. 当质量下降、异常率升高、总成本无法解释或安全边界受威胁时，自动收缩到上一层更保守路径。
