# 方案：Provider 路由、故障切换与 Claude Code 模型职责

> 本方案属于[Provider 路由、故障切换与 Claude Code 模型职责专题](README.md)。核心规则和配置化 routing 已实施；当前运行行为以源码、主文档、双平台 CI 与迭代记录中的真实 smoke 证据为准。

## 1. 背景与目标

本项目通过 Claude Code CLI 调用外部协作者，但 Claude Code 是执行 harness，不是第三个 provider。当前有两个隔离 profile：DeepSeek 与 MiMo。每个 profile 已向 Claude Code 注入 provider 自己的 `ANTHROPIC_DEFAULT_FABLE_MODEL`、`ANTHROPIC_DEFAULT_OPUS_MODEL`、`ANTHROPIC_DEFAULT_SONNET_MODEL`、`ANTHROPIC_DEFAULT_HAIKU_MODEL` 与 `CLAUDE_CODE_SUBAGENT_MODEL` 映射。

实施前 runner 会显式传递 `--model opus`，并在 `provider=auto` 时对任意 Claude CLI 非零退出尝试另一个 provider。实现后已取消前者，并将后者收窄为已归类的可用性故障。

本方案目标：

1. 将 provider 选择与 provider 内部模型选择严格分层。
2. 当一个 provider 真的不可用时，以一次可追溯的跨 provider 切换保护协作连续性。
3. 当两个 provider 都不可用时停止无效外部调用，按确定周期才允许一次恢复探测。
4. 保持 session 隔离、最小交接、快照回滚、expected outcomes 与敏感数据边界不变。

## 2. 目标架构与职责边界

```text
Codex / provider router
  ├─ 是否值得委派、任务风险与验收方式
  ├─ 选择 DeepSeek 或 MiMo
  ├─ 记录 provider health、一次跨 provider 兜底
  └─ 校验 outcomes、处理例外并向用户报告
       ↓ isolated CLAUDE_CONFIG_DIR + provider environment
Claude Code
  ├─ 读取 CC Switch profile 的默认主模型
  ├─ 解析 FABLE / OPUS / SONNET / HAIKU alias
  └─ 在实际创建子代理时使用 CLAUDE_CODE_SUBAGENT_MODEL
       ↓
DeepSeek 或 MiMo endpoint
```

### 2.1 Codex 不再路由内部模型

Codex 的候选键固定为 `deepseek` 与 `mimo`。不得增加 `deepseek-flash`、`deepseek-pro`、`mimo-base` 或 `mimo-pro` 等平级 provider。Flash/Base 与 Pro 的选择、别名映射和子代理模型由各自 provider profile 负责。

这避免把同一 provider 的内部策略拆成多个持续 session，也避免在样本不足的冷启动轮换中把低成本模型与高能力模型错误地同等对待。

### 2.2 取消 runner 的主模型硬编码

`collaborate.py` 的 `invoke()` 不再从 profile 添加 `--model <value>`。`providers.local.json` 中旧的顶层 `model` 字段标记为废弃，并从公开示例与 profile 校验逻辑移除。

runner 仍完整注入 profile 的非密钥 `environment`，包括所有 `ANTHROPIC_DEFAULT_*_MODEL` 与 `CLAUDE_CODE_SUBAGENT_MODEL` 映射，并仍设置该 provider 独立的 `CLAUDE_CONFIG_DIR`。因此：

- 不传 `--model` 不会删除或覆盖 CC Switch 的模型映射；
- Claude Code 使用该隔离 profile 的默认主模型；
- provider 内部是否、何时以及如何使用 FABLE/OPUS/SONNET/HAIKU 或子代理，属于 Claude Code 与 provider 的职责；
- 不把 `--fallback-model` 作为跨 provider 余额/认证失败的机制。

`CLAUDE_CODE_SUBAGENT_MODEL` 只是随 provider profile 传给 Claude Code 的内部模型映射。Claude Code 是否创建子代理、如何把任务分给子代理、子代理使用哪些内部工具，均不经过 Codex 的再次路由或再次脱敏。runner 的 `--tools` 白名单只约束 Codex 启动的 Claude Code 主进程可获得的工具，不把 Claude Code 的内部编排变成 Codex 必须验证、记录或周期探测的能力。

## 3. Provider 选择

### 3.1 无人工评分时的可复现选择顺序

正常选择按下列顺序执行，前一条一旦能唯一决定结果就停止：

1. 用户明确指定 provider：使用指定 provider，不自动跨 provider。
2. 主题存在唯一 active session：恢复其绑定 provider。
3. 排除 `open` health 状态、未满足本轮工具需求、或不允许处理本轮风险等级的 profile。
4. 新主题：读取顶层 `routing`，按 `task_overrides[task_type:mode]`，再按 `default` 选择；支持 `fair_round_robin`、`fixed` 和确定性的 `weighted_round_robin`。
5. 缺少 `routing` 或显式策略为 `fair_round_robin` 时，按健康候选的持久化 cursor 公平轮换；不把 provider 名称、模型宣传或质量分作为隐式偏好。
6. 只有当用户未来主动选择启用“实测学习路由”时，才用同一评估桶 `task_type + mode + risk + context_size + tool_requirement` 的完成率、返工、耗时、成本和可选人工质量分调整默认规则；没有人工评分不能阻碍正常路由。

公平轮换对健康候选 provider key 做稳定排序，使用本地记录的 cursor 逐次选择；因此所有条件相同或没有明确场景规则时，每个健康候选获得相同数量的机会。当前实现的“按 provider 名称作为最终排序”不得继续用作无证据情况下的隐性偏好。

### 3.2 本项目的启动场景规则（缺省公平策略的历史依据）

以下场景表保留为缺省公平策略的历史设计依据，不会覆盖用户配置的 `fixed`、`weighted_round_robin` 或 task override。当前实现不根据未验证的模型能力自动改写 routing policy。

下表是 DeepSeek V4 与 MiMo V2.5 的启动规则，不是“某家模型永远更强”的宣称。两家均支持 1M context、工具调用和 Agent 类任务；规则只把官方资料中差异较明确的能力作为默认偏好。所有涉及密钥、私人资料、客户资料、生产数据、实时网页或已登录账户的任务仍先按现有边界由 Codex 处理，不交给任一 provider。

|场景|默认路径|理由与边界|
|---|---|---|
|本地纯文本的代码审查、算法/数学推理、架构分析、长文档结构化分析、非实时研究|公平轮换|两家公开能力均覆盖长上下文、工具调用、推理和代码/Agent 场景；没有本 harness 的实测证据时，不把 DeepSeek 的公开定位升级为固定优先级。|
|在限定路径和 outcomes 内执行多文件代码修改、排障、测试驱动修复|公平轮换|DeepSeek V4-Pro 和 MiMo-V2.5-Pro 都公开主张 Agent/Coding 优化；公开资料不足以在本 harness 中把其中一家设为永久赢家。轮换也自然积累运行证据。|
|图像、视频、音频与文本混合材料的理解或跨模态整理|Codex native（当前）|MiMo-V2.5 明确具备原生全模态能力，但当前外部协作主进程默认走 Pro alias，不能假定 Claude Code 会自动改用 `mimo-v2.5`。在 provider 自己的 Claude Code 配置明确、且本轮接口能安全传递媒体前，不把此类任务路由给 MiMo。|
|非敏感的个人/生活文字规划、清单、头脑风暴、日常表达|公平轮换|两家都可完成；不把私人日记、私聊、照片、音频或身份信息交给外部 provider。|
|当前信息、联网检索、已登录账户、最终图片/演示/表格/PDF|Codex native|这类任务需要实时或连接器/原生成品能力，不由 DeepSeek/MiMo 的 CLI profile 决定。|
|无法归类的普通文本任务|公平轮换|承认没有足够证据区分，避免伪造能力结论。|

启动规则的资料依据须在 README 中以链接公开：DeepSeek 官方模型/API 文档说明 Pro 的 agentic coding、STEM/coding reasoning 与 Flash 的快速经济定位；MiMo 官方文档说明 V2.5-Pro 的 Agent/Coding 定位以及 V2.5 的原生全模态能力。第三方基准可作为背景参考，但不得覆盖真实的安全边界、工具可用性或用户反馈。

### 3.3 面向 fork 用户的公开规则

实施本方案时，以下同一段规则必须同步写入根 `README.md`、`README.zh.md`、`README.en.md`，以及面向执行者的 `AGENTS.md`、`AGENTS.zh.md` 与 Skill 协议：

> Provider 选择顺序为：用户指定、精确持续 session、健康和能力筛选、`routing` task override/default、缺少配置时的持久化公平轮换。不要按 provider 名称或内部模型名称分配任务；provider 内的模型策略由其隔离 profile/Claude Code 配置负责。可选的实测学习路由只能在积累足够运行证据后启用，不能要求用户先进行人工评分。

README 说明“为什么”、启动规则的资料依据与 fork 配置前提；AGENTS/Skill 写成必须遵守的操作规则，包括 health 状态、用户指定不自动替换、持续 session 不迁移、一次 availability failover 与不得把验收失败当 availability failure。实际实现、文档和测试必须在同一个变更中提交；方案阶段不提前将这些规则表述为当前已运行行为。

## 4. Provider health 与熔断状态

新增本机 ignored 文件 `.ai-collaboration/provider-health.json`。它只保存运行元数据，不能保存 prompt、文件正文、token、完整 stderr 或其他敏感信息。

建议 schema：

```json
{
  "schema_version": 1,
  "providers": {
    "deepseek": {
      "state": "closed | open | half_open",
      "failure_class": "billing | authentication | endpoint | rate_limit | transport | server",
      "consecutive_failures": 0,
      "opened_at": "ISO-8601",
      "next_probe_at": "ISO-8601",
      "last_error_code": "sanitized_code_or_category",
      "last_success_at": "ISO-8601"
    }
  }
}
```

### 4.1 错误分类

Claude Code 的 exit code、结构化错误（若有）和有限长度、脱敏后的 stderr 共同用于分类。仅在以下类别才触发跨 provider 兜底：

|类别|典型信号|含义|
|---|---|---|
|`billing`|余额不足、支付/配额耗尽、HTTP 402 或 provider 明确的计费错误|通常需要用户充值或调整账号。|
|`authentication`|HTTP 401/403、无效认证、权限被拒绝|通常需要更新本地认证。|
|`endpoint`|endpoint 配置错误、协议不兼容、DNS/证书配置失败|通常需要修复 profile。|
|`rate_limit`|HTTP 429 或 provider 明确限流|通常短暂可恢复。|
|`transport`|连接重置、网络不可达、超时|可能短暂可恢复。|
|`server`|HTTP 5xx 或 provider 明确服务端故障|可能短暂可恢复。|

下列情形不是 availability failure，禁止自动换 provider：模型结果不符合 response contract、expected outcomes 失败、测试失败、越界修改、模型理解错误、用户取消，或本地验证命令失败。它们必须按现有规则回滚、标记失败/待审并交回 Codex。

错误匹配器必须按 provider 配置，并只记录归类后的代码；不能把原始 token、URL query、完整错误文本或 provider 原始输出写入 health 文件。

### 4.2 冷却期与恢复

|failure class|初始冷却|连续失败退避|提前恢复|
|---|---:|---:|---|
|`billing`、`authentication`、`endpoint`|24 小时|固定 24 小时|用户明确“已充值/已修复”，或显式 reset health。|
|`rate_limit`、`transport`、`server`|5 分钟|5 分钟 → 15 分钟 → 1 小时 → 6 小时|一次最小探测成功。|

本项目不启动后台轮询。provider 处于 `open` 时，普通任务不会调用它；当 `next_probe_at` 已到，下一次确有外部协作价值的用户请求才将其置为 `half_open`，允许一次最小、无敏感内容的可用性探测。探测成功后关闭熔断并清零连续失败；失败后重新打开熔断并按表退避。

两个 provider 都为 `open` 时，本轮直接由 Codex 完成或向用户报告外部协作暂不可用；在任一 `next_probe_at` 前不再尝试 Claude Code。用户可显式请求 reset，但不应由 reset 自动触发真实任务重放。

## 5. 跨 provider 故障切换

仅同时满足以下条件时，允许一次从当前 provider 切换到另一健康 provider：

1. 本轮为 `provider=auto`，不是用户明确指定；
2. 主 provider 发生第 4.1 节定义的 availability failure；
3. 当前任务尚未因 outcomes、验证或越界而失败；
4. 存在另一健康 provider；
5. 本轮尚未发生 provider failover。

对于 `execute`，先恢复本轮 checkpoint，再向备用 provider 发起新 session；不得携带原 provider 的 session ID。对于持续主题，Codex 基于现有一页 topic state、最小 handoff、范围限制、outcomes 与未决事项建立 continuity handoff，并在新的 session registry 记录：

```json
{
  "provider_failover": {
    "from": "deepseek",
    "to": "mimo",
    "failure_class": "billing",
    "source_session_key": "...",
    "continuity": "new_session_from_topic_state"
  }
}
```

该记录只能包含 session key、provider 和归类，不能存 session transcript 或原始故障文本。原 session 保持原 provider 归属；不得重写为备用 provider。

## 6. 可观测性与用户反馈

每次外部调用的紧凑回传增加：

- `provider_health_before` 与 `provider_health_after`；
- `failure_class`（仅归类结果）；
- 是否发生 `provider_failover`、来源与目标 provider；
- 是否为 half-open probe；
- 冷却到期时间（仅在 provider open 时）。

面向用户的报告应说明“DeepSeek 因计费错误不可用，已一次性切到 MiMo”或“两个 provider 处于冷却期，本轮未发起外部调用”；不得显示 token、完整错误或未脱敏 provider 输出。

## 7. 实施步骤

1. **Profile 与 invocation**：停止添加 `--model`；弃用 profile 顶层 `model`；保留并测试环境模型映射及隔离 `CLAUDE_CONFIG_DIR`。
2. **Health store**：实现 schema 读写、错误分类、状态转换、reset 与过期/half-open 判定。
3. **Router**：在 metrics 选择前排除 `open` provider；所有候选都不可用时返回明确的 local diagnosis。
4. **Failover**：仅对 availability failure 执行一次跨 provider 新 session；execute 先回滚 checkpoint；持续主题生成 continuity handoff。
5. **回传与日志**：增加脱敏 health/failover 摘要，保留原有 compact 上限。
6. **验证与文档同步**：先 fake launcher 覆盖状态机、预设场景路由、公平轮换、回滚和双 provider 冷却；再同步根 README 的中英文说明、AGENTS 双语、Skill/协议、主文档、DEC、测试用例与迭代记录。不将真实 provider 失败文本写入版本库。Claude Code 内部子代理不单列探测或验收项。

## 8. 验收用例

以下 PRF-09、PRF-10 和 PRF-12 验证的是缺少 routing 或显式使用 `fair_round_robin` 时的兼容基线；配置化策略的覆盖行为由技术设计中的 TC-94 至 TC-102 验证。

|编号|场景|期望结果|
|---|---|---|
|PRF-01|DeepSeek profile 含 FABLE/OPUS/SONNET/HAIKU/SUBAGENT 映射|runner 注入映射但 command 不含 `--model`。|
|PRF-02|MiMo profile 同上|runner 注入映射但 command 不含 `--model`。|
|PRF-03|用户指定 DeepSeek，返回 billing 错误|记录 DeepSeek `open`；不自动调用 MiMo。|
|PRF-04|`provider=auto` 的新主题，DeepSeek 返回 billing 错误|checkpoint 恢复；仅新建一次 MiMo session。|
|PRF-05|持续 DeepSeek session 发生 billing 错误|原 session 不变；MiMo 以 continuity handoff 新建 session。|
|PRF-06|execute outcomes 失败|回滚；不切换 MiMo。|
|PRF-07|两个 provider 都处于冷却期|不启动 Claude Code；返回下次可探测时间。|
|PRF-08|到期后的 half-open probe 成功|关闭熔断、清零失败计数，再正常路由。|
|PRF-09|纯文本长文档分析或算法/数学推理|在健康 provider 间按该场景 cursor 公平轮换；回传包含 `route_basis: starter_policy_text_reasoning_rotation`。|
|PRF-10|限定路径的多文件代码 execute|在健康 provider 间按该场景 cursor 公平轮换；回传包含 `route_basis: starter_policy_coding_execute_rotation`。|
|PRF-11|图像、视频、音频或混合媒体输入|当前保持 Codex native；不得假定 provider 内部会自动从 Pro 切换到 MiMo-V2.5。|
|PRF-12|无法归类的普通文本任务|按健康 provider cursor 公平轮换；不得因 provider 名称固定偏向任一方。|
|PRF-13|实现变更完成|README 双语、AGENTS 双语、Skill/协议、主文档、DEC、测试用例和迭代记录均包含同一通用 provider 选择原则和启动规则。|

## 9. 非目标

- 不修改 CC Switch 的全局当前 provider。
- 不将 Flash/Base/Pro 变为 Codex 的四个平级路由候选。
- 不跨 provider 复用 Claude Code session ID。
- 不在后台持续探测、自动重放任务或进行多轮 provider 辩论。
- 不因模型输出质量、验收失败或越界修改而自动换 provider 重试。
- 不读取、记录或传播 token、完整 provider 输出或完整 session transcript。
- 不干预、单独脱敏、记录、探测或周期复验 Claude Code 的内部子代理；它们不是 Codex 的平级协作者。
