# 外部代理持续协作 Skill：技术方案

## 1. 架构

```text
用户请求
  -> 根据 SKILL.md metadata 发现并选中 external-agent-collaboration Skill
  -> 选中后的任务分类：Codex 原生 / 直接 / 外部协作
  -> 外部目标解析：harness -> provider/profile -> session -> permission policy
  -> 交接包 + 本地会话注册表
  -> harness adapter
       -> Claude Code CLI（当前：DeepSeek/MiMo profile）
       -> Antigravity CLI（P2 只读 adapter 已实现；未进入自动路由）
  -> 统一结构化结果、受控文件变更和日志
  -> Codex 按风险整合与校验
```

Claude Code 是本地执行 harness，不用于标识底层模型。报告中使用“<provider> 协作者”，并记录 launcher/profile，而非把所有执行结果称作 Claude。Antigravity 同样是独立 harness，而不是 Claude Code 的 provider、profile 或 session 变体。官方 headless 行为的设计基线见 [headless CLI 参考资料](headless-cli-references/README.md)。

```text
  logs/

  harness-capabilities.json       # planned, per harness/profile/platform
```

provider 配置分为两层：受版本控制的 `.ai-collaboration/providers.shared.json` 保存不含 token 的 provider 定义；Git 忽略的平台 local profile 保存可直接编辑的认证和本机路径。加载顺序固定为 shared、shared 的当前平台 override、通用 local、当前平台 local。推荐文件名为 `providers.local.macos.json`、`providers.local.windows.json` 和（需要时）`providers.local.posix.json`。平台文件可直接包含 `auth_token`、launcher 与 `CLAUDE_CONFIG_DIR`；是否通过用户自己的私有同步机制同步这些文件由用户决定。

项目不把环境变量、macOS Keychain、Windows Credential Manager 或其他系统凭据库作为要求或默认实现。`migrate_portable_profiles.py --apply` 仅将 legacy profile 的直接 token 复制到当前平台 local profile；`--cleanup-legacy` 只有在两个平台 profile 都已存在时才可清空旧通用文件，并先在用户目录创建非同步备份。无论配置文件是否同步，token 均不得进入 Git、handoff、输出、日志、测试 fixture 或外部提示词。

## 3. Provider profile

每个 profile 的最小字段：

```json
{
    "mimo": {
      "config_dir": "<absolute-path-to-isolated-claude-config>",
      "launcher": "claude",
      "required_environment": ["ANTHROPIC_AUTH_TOKEN"],
    "environment": {
      "ANTHROPIC_BASE_URL": "https://provider.example/anthropic",
      "ANTHROPIC_MODEL": "provider-model[1M]"
    }
  }
}
```

端点与模型映射按用户已验证的服务商配置填写；顶层 `model` 不再是 profile 字段。运行时脚本只将当前平台 local profile 的 token 用作对应 API endpoint 的认证，不把它传入协作者提示词、输出或日志，也不传 runner-level `--model`。`config_dir_relative_to_home` 可用于无密钥 shared 定义；平台 local profile 也可直接指定绝对 `config_dir`。脚本不会复制 `~/.claude`、读取 CC Switch 数据库或记录 token。启动时设置对应 `CLAUDE_CONFIG_DIR`，使 transcript、memory 和 session lookup 隔离。认证方式、解析后的目录、平台与 launcher 指纹均进入信任 fingerprint；任一变化都要求用户重新批准。

## 4. 会话注册表

`sessions.json` 使用以下最小 schema：

```json
{
  "schema_version": 1,
  "sessions": [{
    "key": "brand-strategy-mimo",
    "topic": "品牌策略",
    "provider": "mimo",
    "model_profile": "mimo",
    "working_directory": "/absolute/project/path",
    "workspace_identity": "sha256-of-normalized-local-workspace",
    "host_platform": "windows | macos | posix",
    "session_id": "UUID",
    "initial_toolset": ["Read", "Glob", "Grep", "Edit", "Write"],
    "status": "active",
    "created_at": "ISO-8601",
    "last_used_at": "ISO-8601"
  }]
}
```

解析顺序为：用户指定 session key > 完整主题绑定 > 同主题唯一 active session > 新建会话。出现多个候选时停止并要求 Codex 选择，绝不使用 CLI `--continue`。不同 `host_platform`、工作区 identity 或无法识别的旧路径一律不得恢复；保留 topic state 后在当前主机创建新 session。

## 5. 调用协议

`collaborate.py` 接收 action、provider、topic、working directory、handoff file、可允许路径和可允许校验命令。它执行：

1. 校验参数、工作目录、profile 和敏感路径规则。
2. 校验 `trusted-providers.local.json` 中当前非密钥 profile fingerprint；如记录缺失或 profile 变化，Codex 按维护者持续授权先写入该非密钥本地记录，再启动 Claude Code。该流程不绕过宿主的最终外发审批。
3. 创建交接包、日志目录与执行前快照。
4. 新会话当前用 `claude -p <prompt> --output-format json --permission-mode dontAsk`；续接用同样命令加 `--resume <session_id>`。下一阶段改为同时传 CLI 原生 `--json-schema`，优先读取 `structured_output`，避免仅靠提示词要求 JSON。非交互 runner 不使用 `acceptEdits` 或 `plan` 执行写任务；`dontAsk` 的拒绝返回 `blocked_by_permission`，而不是等待终端批准或静默完成。
5. 对 `consult`/`critique` 限制为 `Read,Glob,Grep`；对新建 execute session 提供 `Edit,Write`。当 outcomes 要求创建当前不存在的文件时，执行器自动复用或更新当前主机的能力档案；旧 session 缺 `Write` 时自动 `--fork-session` 到继承上下文的新 session。只有已实测的 POSIX shell 才可使用精确 Bash 创建白名单；Windows 或未知 shell 一律拒绝该兜底并要求 native `Write`、fork 或新建 session。
6. 用 Python 进程超时控制 wall-clock 时长；不使用本机 CLI 未列出的 `--max-turns` 参数。
7. 由对应 harness adapter 解析 JSON，归一化为统一 result envelope 后，原子写入 session registry、结果和审计日志。
8. 比较执行前后快照，拒绝或标记越界修改。

### 5.1 Expected outcomes

每个 `execute` 必须传入 project-relative 的 outcomes JSON。执行器支持：`file_exists`、`file_contains`、`file_equals`、`changed_paths`、`command_succeeds` 和 `json_schema`。`command_succeeds` 优先使用与 `--validation-argv` 完全一致的 JSON 参数数组，并以 `shell=False` 执行；旧 string `command` 仅在逐字匹配显式 `--validation-command` 时保留。JSON Schema 使用受限且可审计的本地子集。

模型最终文本不是成功证据。执行器在外部调用后检查 outcomes；任何一项失败时恢复本次任务的完整变更集，记录失败原因并返回 `failed`。详细 schema 见 Skill 的 `references/expected-outcomes.md`。

外层 Codex 沙箱与审批仍然生效；外部 CLI 不拥有绕过 Codex 安全边界的权限。

## 6. 自动路由与故障处理

隐式选中与实际委派是两个阶段：全局 Skill 的 `SKILL.md` frontmatter 根据恢复主题、独立/第二模型评审、全仓/关联模块/多文件工作或边界明确的独立实施等信号，决定是否选中本 Skill；选中后才运行 `classify_task.py` 和 provider 配置检查。分类器是调用前的安全门，不负责让 Skill 出现在 Codex 的候选中。简单问答、常规评审、小型单文件修改以及未配置 provider 的项目不进入外部调用。

- 明示供应商：使用该供应商。
- 已绑定主题：恢复绑定供应商。
- 新主题：在健康 provider 间按 `task_type:mode` cursor 公平轮换；当前不依据评分选择 provider。
- runner 不传 `--model`；provider 内部 FABLE/OPUS/SONNET/HAIKU/SUBAGENT 映射由隔离 CC Switch/Claude Code profile 决定。
- 同一 provider 出现 billing、authentication、endpoint、rate-limit、transport 或 server 可用性错误：只记录归类和冷却时间；仅允许一次另一健康 provider 的故障转移。billing/authentication/endpoint/configuration 冷却 24 小时；暂时错误按 5 分钟、15 分钟、1 小时、6 小时递增。
- 任务、response contract、outcome、范围检查失败或未分类错误：不跨 provider 重试，返回 Codex 处理。没有后台探测；冷却到期后仅由原本允许的下一次调用尝试恢复。

每次潜在委派先由 `classify_task.py` 输出 task type、mode、风险、上下文规模、工具需求和 delegation。实时/连接器/原生成品固定留在 Codex；敏感内容禁止交接；小任务直接处理。`provider_routing.py` 只保存 provider、任务分类、状态、CLI 返回的成本、耗时、工具拒绝、返工、人工质量分和采纳结果等元数据，不保存提示词、token 或文件正文。`.ai-collaboration/provider-health.json` 只保存 failure kind、次数和 retry time，不保存完整 stderr、URL query 或任何业务内容。内部子代理不是独立安全边界：外部调用前的 handoff 脱敏覆盖该次 Claude Code 执行；当前不以其为由增加单独 probe 或周期验证。

## 7. 文件修改控制

`execute` 不以提示词作为唯一约束。脚本必须执行路径解析与差异检查：

- 允许目录：当前项目与用户本轮明确指定的子目录；
- 禁止匹配：`.env`、`.env.*`、`secrets/`、`credentials/`、私钥、生产数据导出、`.git/`；
- 禁止命令：commit、push、merge、reset、rebase、deploy、publish、全局安装及数据库/云端破坏性命令；
- 执行前保存目标文件的哈希与文本快照；
- 执行后输出修改清单和 unified diff；发现越界即把状态标记为 `needs_review`，不宣称成功。

## 8. 可观测性与隐私

日志记录时间、action、provider、session key、退出码、耗时、变更路径、校验状态和已脱敏错误类别。日志不记录 prompt 全文、认证信息、`.env` 内容或外部模型原始隐藏推理。交接包仅包含完成本轮所需的背景与允许文件。

## 9. 能力探测

`probe_capabilities.py` 用 ephemeral session 在 gitignored 的 `capability-lab/` 运行最小新建文件实验，记录原生 `Write` 与（仅在已确认 POSIX shell 时）精确 Bash 创建兜底是否实际成功。它在首次需要创建文件/目录、记录超过七天、CLI/profile/平台变化、或工具缺失失败后运行；不在每次任务前运行。探测更新 `.ai-collaboration/provider-capabilities.json`，其中必须带 host platform 与 shell evidence，而不是让模型自行改写 Skill 的安全规则。探测结论只描述新 session；持续 session 同时保存其创建时的 `initial_toolset`，以避免把新工具错误地假定为旧会话可用。

## 10. 主题生命周期

每个新 persistent session 同步登记到 `topics.json`，包括 topic、provider、profile、working directory、session key/ID 和可选父 session。`--fork-session` 由 Claude Code 的真实 `--resume … --fork-session` 组合实现，子 session 不覆盖父 session。`archive_session.py --session-key <key>` 将 session 标为 archived，并在 `.ai-collaboration/archives/` 写入可供下一位协作者读取的非敏感索引；归档时不复制 token 或 `.env` 片段。

## 11. 一次性独立审查

`review_execution.py --run-id <id>` 只接受已 completed 的 execute 输出，要求显式选择另一 provider（也可明确指定），生成仅含变更路径和 outcomes 摘要的 read-only handoff，并把 critique 原始结果封存到 `reviews/`。该流程没有“审查者再通知执行者”的自动步骤，因此不会形成递归或自动辩论。

2026-07-28 的实测：MiMo 与 DeepSeek 的新 ephemeral session 均成功使用原生 `Write` 新建文件。首条 MiMo 长会话在 `Write` 被加入执行器之前创建，因此恢复后只具有 `Read,Glob,Grep,Edit`；其精确 `touch` 白名单兜底已验证成功。这是一次通用的 session 工具集陈旧样本，不是 MiMo 专属路由规则；任何 provider 的旧 session 都按同一机制处理。

## 12. 协作效能与最小持久化（P0–P3 已实现）

实施以 `docs/专题/2026-07-29-协作效能优化/方案.md` 为设计输入，并以专题入口记录的状态和证据校验进展。P0 已为 `collaborate.py` 增加 `return_mode`：默认 `compact` 将 stdout 限制为最多 8 KiB 的 envelope；`structured` 只接受受限 response schema；`file_only` 返回索引和完整 record 的 hash；`debug` 才返回完整 record。完整 CLI JSON 始终写入 ignored runtime output，默认不打印回 Codex。response contract 不合格时记录 `result_contract_failed`，但 execute 是否完成仍由 machine outcomes、范围检查与验证命令判定。默认回传中的常见 token 形态会脱敏。

P0 的 bootstrap 会创建但不覆盖 `project-context.md`、`decisions.md` 和 `topics/`。每个非 ephemeral run 只写入对应主题的一页状态：目标、范围、状态、下一步、证据路径和 stop rule；不保存完整 handoff、模型推理、聊天或 provider output。`sessions.json` 是本机 provider/session 映射，整个 `.ai-collaboration/` 均为 ignored local state。完整 handoff、output、日志、快照和 capability 实验为带保留期的 runtime cache，默认不读入后续交接或 Codex 上下文。

P1 已实现本地 batch 控制面：`batch.py plan` 扫描非敏感文本、生成 manifest、小样本与按文件数/字节数分片；`batch.py reduce` 校验 JSONL 的路径/hash/schema、拒绝未知或重复行，并输出 pending、异常、抽样和 summary。所有 batch 状态只允许写入 ignored `.ai-collaboration/`。受控外部只读 worker 已完成真实小样本验证；不允许单次 execute 覆盖超过快照上限的根目录。P2 已提供分类效能字段、回传比/预算建议和非敏感指标记录；Codex-only 对照数据按任务持续积累，不将样本不足解释为结论。P3 的 runtime 保留期维护和保守收缩健康信号由 `maintain_runtime.py` 提供。

## 13. 文档治理

四份主文档是当前有效规范，持续更新。实质决策以 `docs/决策记录/DEC-YYYYMMDD-<slug>.md` 版本化，记录取舍和影响范围；`docs/迭代记录.md` 记录实际变更和验证。Git 历史是逐字回溯来源，主文档版本号只用于里程碑、对外契约/schema 变更或基线冻结。

专题材料放在 `docs/专题/YYYY-MM-DD-<slug>/`，以 `README.md` 作为元数据和导航入口。入口保存不可变的讨论基线及可变的实施状态；方案、调研和验收附件只在该目录内存放。实现结论进入主文档，已完成或被取代的专题在入口注明最终状态和替代关系，不通过移动或删除材料来掩盖历史。

## 14. Headless multi-harness architecture（规划）

### 14.1 不可混淆的边界

|层|职责|当前状态|
|---|---|---|
|Harness|启动本地 CLI、适配会话/权限/输出/错误语义。|Claude Code 已实现；Antigravity P2 只读 adapter 已实现，未进入自动路由。|
|Provider / account target|决定请求发送到哪一家已配置服务或本机账号。|Claude Code 下的 DeepSeek/MiMo 已实现；Antigravity 使用其自身账号与目标。|
|Model profile|隔离配置中的模型、努力度、agent 或内部 alias。|Claude Code profile 已实现，runner 不传 `--model`；Antigravity P2 由固定本地 profile 管理，任务分类器不能随意钉模型。|
|Session|特定 harness 返回的 `session_id` 或 `conversation_id`。|必须携带 `harness + harness_profile + provider + host_platform + workspace_identity`，绝不跨 harness 恢复。|
|Permission policy|工具白名单、路径/命令限制和非交互拒绝语义。|每个 adapter 显式实现；任何“软拒绝但进程退出 0”都映射为 `blocked_by_permission`。|
|Result envelope|统一 `status`、session identity、structured result、usage、工具/权限事件和脱敏错误类别。|在 adapter 边界归一化；不得保存完整 prompt、凭证或原始事件流。|

现有 `provider_routing.py` 只服务 Claude Code 下 DeepSeek/MiMo 的公平轮换。引入 Antigravity 后不得把它硬塞为第三个 provider；先新增 `harness_router`，再让 provider router 在已选 Claude Code harness 内工作。health、trust、capability、session 和 metrics 的键均必须包含 harness/profile/platform，避免不同 CLI 的错误、权限和会话互相污染。

### 14.2 Claude Code 优化（P0：macOS 主路径已验收，Windows 待执行）

1. 已建立 `ClaudeCodeAdapter`，将当前 `invoke` 命令、outer JSON 解析、`--resume`、profile environment 与原生 schema argv 封装在单一接口中；`permission_denials` 仍由 runner 统一映射为 `blocked_by_permission`，行为保持不变。
2. 已为标准 response contract 传入 Claude Code 的 `--json-schema`，优先读取 CLI `structured_output`；仅当该字段缺失时，才回退解析旧 `result` JSON。若 `structured_output` 存在但不合约，不以文本结果掩盖冲突。实际 smoke 已表明，仅靠 prompt 可能在 JSON 外附加文本。
3. 已实现 opt-in `stream-json` 诊断模式：只保存启动、event type 计数、内部 retry、plugin/MCP failure、权限信号与终态等脱敏元数据；默认 compact 模式不保存完整流、prompt、模型文本或子代理文本。
4. 不默认添加 `--bare`。它可作为经过本机验证的 deterministic read-only/CI profile 选项，但会跳过自动发现的 plugins、skills、MCP 与配置；不得破坏用户隔离 CC Switch profile 的能力。
5. 保持 `dontAsk` 与精确 `--tools/--allowed-tools`；不因 headless 文档存在 `acceptEdits` 示例而放宽受控 execute 边界。

`sensitivity.py` 同时实现 value-aware 的前置分类与 runner 最终 handoff scanner：实际 credential value/assignment、私钥块、明确 `.env` 正文和客户/生产数据外发会阻断；政策性否定文字不会阻断；无法确认的引用返回 `requires_redaction`。这两个 gate 独立运行，分类通过不等于允许外发。

macOS 已完成真实最小 smoke：`stream-json` terminal `structured_output` 合约有效、保存的 session 以精确 ID 成功恢复，且没有项目文件变更。以 `pwd` 和 Claude 文档列为 `dontAsk` 拒绝对象的 `AskUserQuestion` 各做一次真实 permission smoke 时，当前 CLI/model 都没有发起工具调用，故没有可观察的 `permission_denials`；不把该结果误报为拒绝。`permission_denials -> blocked_by_permission` 的归一化仍由 fake launcher 回归覆盖。Windows 回归仍待执行，因此本节不能整体标记为双平台完成。

### 14.3 Antigravity adapter（P2：macOS 真实 smoke 已完成，Windows 待验收）

`AntigravityAdapter` 的已验收入口是只读的 `consult_antigravity.py`：仅接受 `consult`/`critique`、强制 `--mode plan`、使用 `agy -p --output-format json --json-schema` 与指定 `--conversation`，保存其 `conversation_id`，而非 Claude session ID。P3 的 `execute_antigravity.py` 是独立、受限且当前 blocked 的实验入口，不是自动路由候选。adapter 还可解析 `stream-json` 的 `init`、`step_update` 与 terminal `result`，但只归档无内容的 lifecycle 计数和终态。`harness-profiles.local.json` 仅可保存非密钥的 launcher/mode/model/effort/agent；Antigravity 认证仍使用用户先前交互登录留下的缓存。调用前必须以 `trust_harness.py --profile <name> --approve` 对当前 profile fingerprint 做本地批准。模型、effort、agent 若要设置，必须在该 profile 固定；任务分类不直接选择具体 model slug。macOS 已通过一条无工具、无敏感的真实 schema smoke；执行 `agy` 的宿主必须允许其写用户日志并绑定 localhost，Codex sandbox 不满足该条件。

Antigravity 文档描述的默认 headless 软拒绝可能仍以进程 0 结束，adapter 因此同时检查 terminal status、error 与 stderr 中的 permission/approval 信号。`--dangerously-skip-permissions` 不得用于主工作树自动执行；仅维护者显式启用的 isolated full-auto 实验可传该 flag。P3 的独立受控执行器已具备路径快照、outcome 和回滚边界，但不进入自动路由。macOS 与 Windows 的同一单文件 P3 smoke 均返回有效结构化结果且未写文件，因此 P3 仍 blocked；终态 `SUCCESS` 派生的 `permission_state: allowed` 不能当作写入工具已调用的证据。下一步是在不保存内容的前提下记录 stream-json 工具可用性和步骤类型，再定位 headless agent/tool routing。完成一次交互认证且当前 profile 已信任后，Codex 可直接运行最小、无敏感的 read-only consult 作为工程验证；受控 execute 则必须有明确、可回滚的路径和命令范围。

### 14.4 兼容迁移与回滚（WP-11.2 基础已实现）

已新增 `HarnessAdapter` 最小协议，以及 `harness_state.py` 的 Claude-first state identity。新 Claude session、trust、health、capability 与 metric event 都写入 `harness`、`harness_profile` 和 `state_identity`；session 另写 `external_session_id` 与 `session_kind`，但保留旧 `session_id` 以兼容既有 Claude Code registry。

`migrate_harness_state.py` 默认只报告会标注多少旧 record；只有显式 `--apply` 才会先在 ignored `.ai-collaboration/backups/` 备份、再写入标注。它不会推测 Antigravity conversation 或改写其已存在的 harness record。`EXTERNAL_AGENT_HARNESS_STATE=1` 是当前的 guard feature flag：启用后，同主题的 foreign-harness active session 会在 Claude 路由前 fail-closed；默认仍是既有的 Claude Code 路由。任一 adapter 的本机配置、CLI 版本、平台、权限语义或非密钥 profile 变化都使其 trust/capability record 过期；失败可禁用该 adapter，不影响既有 Claude Code session。该基础已经可与 Antigravity adapter 的 fake launcher 并存；全量的双 harness 运行时隔离验收仍留在 P2/P4 集成阶段，不能把基础层当作完整 role router。

## 15. 分类与目标选择（规划）

分类器不以“某模型天然更擅长某类任务”的未验证结论做分配，但必须有可预期的默认行为。设计采用**角色路由**，而不是把所有可调用目标放进一个公平轮换池：DeepSeek/MiMo 是同一 Claude Code harness 内、同类权限与会话语义下的可替代 provider，因此保持公平轮换；Antigravity 的会话、认证与权限语义不同，按独立角色选择。

|优先级与条件|默认目标|对用户的含义|
|---|---|---|
|敏感内容、实时事实、连接器数据、图像/表格/PDF/最终办公产物|Codex 原生 / 禁止外发|不把不该离开 Codex 的任务交给任一 harness。|
|已有精确 active session|该 session 所属 harness|持续主题永远优先连续性；不会因新规则迁移旧会话。|
|需要编辑项目、运行受控命令、复用 CC Switch profile/plugin/MCP，或普通的新项目协作任务|Claude Code|这是默认的“项目协作者”角色；新主题仍只在健康 DeepSeek/MiMo 间公平轮换。|
|无历史会话、只读、明确要求独立审查/第二方案/反方意见/风险清单，且 Antigravity P2 已在当前平台验证|Antigravity|这是默认的“独立审查者”角色；创建独立 conversation，不读取或续接 Claude 会话。|
|任务明确需要用户配置的 Antigravity agent/profile，且该 profile 已批准和验证|Antigravity|尊重用户已配置的专门 agent，但 model/effort/agent 固定在 profile，不由分类器临时钉值。|
|简单问答、常规评审、小型单文件改动|Codex 直接处理|不为了使用第二 harness 增加成本和延迟。|
|Antigravity 尚未安装、认证、批准、或当前 Windows/macOS capability 未验证|不选 Antigravity|独立审查请求改为 Codex 处理或报告未就绪；不得暗中把未验证 CLI 拉起。|

因此，Antigravity 落地后会有明确的自动分配场景：**新的、无敏感、只读的独立审查与替代方案任务**。例如“从与现有方案无关的角度审查该架构风险”“为同一需求提出第二套方案”，在没有要恢复的 Claude 会话时，自动选择已就绪的 Antigravity。相反，“继续项目”“实现/修改/测试”“普通新项目协作”默认仍走 Claude Code + DeepSeek/MiMo pool。

高风险 execute 的组合规则是“Claude Code 执行，Antigravity 一次只读 critique”，而不是让两个 harness 竞争执行同一任务。用户明确指定 harness 永远覆盖默认角色；availability fallback 只有在该任务 policy 显式列出允许替代 harness 时发生一次，且必须在结果中标记角色降级。contract、outcome、scope 或 permission failure 不得触发跨 harness 替换。

只有未来在相同、无敏感且用户认可的基准集上积累足够质量、返工、成本、延迟和稳定性证据，并新增明确 DEC 后，才可扩大 Antigravity 的默认角色或改变这一角色路由。它不会自动变成与 DeepSeek/MiMo 等权的全任务公平候选。

## 16. macOS 与 Windows 是每次变更的验收维度

任何 harness、profile、session、shell、权限、启动命令、迁移器、测试或文档规定的命令都须在设计时填写 platform impact：macOS、Windows、not affected 的依据。验证要覆盖路径规范化、launcher discovery、非交互认证失败、权限拒绝、JSON/stream 输出、超时、session migration 和 fake CLI。不得以 macOS/POSIX 成功或 API 文档示例替代 Windows 行为证据。

## 17. Execute 权限编排

权限独立于 harness 路由：`readonly`、最小预授权的 `controlled-execute`、以及维护者显式启用的 `local-full-auto`。AGY 仅在后者传 `--dangerously-skip-permissions`；Claude 默认 `acceptEdits + dynamic allowedTools`。所有模式仍由 runner 的路径、命令、checkpoint、outcome 与回滚机械约束。

macOS 的 isolated full-auto P3 已验证：临时工作区只含一个目标文件，effective mode 为 `always-proceed`，且 `write_to_file` 可用，但目标仍未被写入。因此 P3 不是 settings 或主工作树范围问题，而是当前 AGY headless agent/tool 行为限制。系统固定 AGY 为只读独立协作者，Claude Code 为唯一自动 execute harness，直到同一最小实验获得相反证据。
