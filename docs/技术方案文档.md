# 外部代理持续协作 Skill：技术方案

## 1. 架构

```text
用户请求
  -> Codex + external-agent-collaboration Skill
  -> 路由与会话解析
  -> 交接包 + 本地会话注册表
  -> provider launcher (locally configured provider)
  -> Claude Code CLI (-p, JSON, --resume 可选)
  -> 结构化结果、受控文件变更和日志
  -> Codex 按风险整合与校验
```

Claude Code 是本地执行 harness，不用于标识底层模型。报告中使用“<provider> 协作者”，并记录 launcher/profile，而非把所有执行结果称作 Claude。

## 2. 文件布局

```text
.agents/skills/external-agent-collaboration/
  SKILL.md
  SKILL.zh.md
  agents/openai.yaml
  scripts/collaborate.py
  scripts/doctor.py
  scripts/probe_capabilities.py
  scripts/classify_task.py
  scripts/provider_routing.py
  scripts/archive_session.py
  scripts/review_execution.py
  scripts/bootstrap.py
  references/collaboration-protocol.md
  references/providers.local.example.json

.ai-collaboration/
  project-context.md
  decisions.md
  topics/<topic>.md
  sessions.json（本地 ignored）
  runtime/ (handoffs, outputs, logs, snapshots, reviews)
  provider-metrics.json
  handoffs/
  outputs/
  logs/
  snapshots/
  provider-capabilities.json
```

`providers.local.json` 是本机私有配置，应放在 `.ai-collaboration/` 且加入 `.gitignore`。当前用户明确授权在其中保存直接 token；该文件不得提交、同步、放入交接包、日志或提示词。endpoint、模型映射与非密钥开关也仅在本地 profile 中保存。

## 3. Provider profile

每个 profile 的最小字段：

```json
{
  "mimo": {
    "config_dir": "/Users/<user>/.claude-mimo",
    "launcher": "claude",
    "model": "opus",
    "auth_token": "local-only-secret",
    "environment": {
      "ANTHROPIC_BASE_URL": "https://provider.example/anthropic",
      "ANTHROPIC_MODEL": "provider-model[1M]"
    }
  }
}
```

端点与模型 ID按用户已验证的服务商配置填写。运行时脚本只将本地 token 用作对应 API endpoint 的认证，不把它传入协作者提示词、输出或日志。脚本不会复制 `~/.claude`、读取 CC Switch 数据库或记录 token。启动时设置对应 `CLAUDE_CONFIG_DIR`，使 transcript、memory 和 session lookup 隔离。

## 4. 会话注册表

`sessions.json` 使用以下最小 schema：

```json
{
  "schema_version": 1,
  "sessions": [{
    "key": "brand-strategy-mimo",
    "topic": "品牌策略",
    "provider": "mimo",
    "model_profile": "mimo",
    "working_directory": "/absolute/project/path",
    "session_id": "UUID",
    "initial_toolset": ["Read", "Glob", "Grep", "Edit", "Write"],
    "status": "active",
    "created_at": "ISO-8601",
    "last_used_at": "ISO-8601"
  }]
}
```

解析顺序为：用户指定 session key > 完整主题绑定 > 同主题唯一 active session > 新建会话。出现多个候选时停止并要求 Codex 选择，绝不使用 CLI `--continue`。

## 5. 调用协议

`collaborate.py` 接收 action、provider、topic、working directory、handoff file、可允许路径和可允许校验命令。它执行：

1. 校验参数、工作目录、profile 和敏感路径规则。
2. 创建交接包、日志目录与执行前快照。
3. 新会话用 `claude -p <prompt> --output-format json`；续接用同样命令加 `--resume <session_id>`。
4. 对 `consult`/`critique` 限制为 `Read,Glob,Grep`；对新建 execute session 提供 `Edit,Write`。当 outcomes 要求创建当前不存在的文件时，执行器自动复用或更新能力档案；旧 session 缺 `Write` 时自动 `--fork-session` 到继承上下文的新 session。仅实测原生 `Write` 不可用时，才生成精确 Bash 创建白名单。
5. 用 Python 进程超时控制 wall-clock 时长；不使用本机 CLI 未列出的 `--max-turns` 参数。
6. 解析 JSON，原子写入 session registry、结果和审计日志。
7. 比较执行前后快照，拒绝或标记越界修改。

### 5.1 Expected outcomes

每个 `execute` 必须传入 project-relative 的 outcomes JSON。执行器支持：`file_exists`、`file_contains`、`file_equals`、`changed_paths`、`command_succeeds` 和 `json_schema`。`command_succeeds` 必须逐字匹配一个显式 `--validation-command`；JSON Schema 使用受限且可审计的本地子集。

模型最终文本不是成功证据。执行器在外部调用后检查 outcomes；任何一项失败时恢复本次任务的完整变更集，记录失败原因并返回 `failed`。详细 schema 见 Skill 的 `references/expected-outcomes.md`。

外层 Codex 沙箱与审批仍然生效；外部 CLI 不拥有绕过 Codex 安全边界的权限。

## 6. 自动路由与故障处理

- 明示供应商：使用该供应商。
- 已绑定主题：恢复绑定供应商。
- 新主题：读取本地评估数据；不足时平衡轮换。
- 同一 provider 出现认证、端点或协议错误：记录错误；仅允许一次另一 provider 的故障转移。
- 任务失败、超时或生成越界修改：不循环重试，返回 Codex 处理。

每次潜在委派先由 `classify_task.py` 输出 task type、mode、风险、上下文规模、工具需求和 delegation。实时/连接器/原生成品固定留在 Codex；敏感内容禁止交接；小任务直接处理。`provider_routing.py` 只保存 provider、任务分类、状态、CLI 返回的成本、耗时、工具拒绝、返工、人工质量分和采纳结果等元数据，不保存提示词、token 或文件正文。`assess_run.py` 只按 run ID 补充 0–5 质量分、采纳与返工次数。新主题冷启动严格轮换；同类样本达到 3 条后按人工质量、完成率、耗时排序，并在输出中写明选择依据。

## 7. 文件修改控制

`execute` 不以提示词作为唯一约束。脚本必须执行路径解析与差异检查：

- 允许目录：当前项目与用户本轮明确指定的子目录；
- 禁止匹配：`.env`、`.env.*`、`secrets/`、`credentials/`、私钥、生产数据导出、`.git/`；
- 禁止命令：commit、push、merge、reset、rebase、deploy、publish、全局安装及数据库/云端破坏性命令；
- 执行前保存目标文件的哈希与文本快照；
- 执行后输出修改清单和 unified diff；发现越界即把状态标记为 `needs_review`，不宣称成功。

## 8. 可观测性与隐私

日志记录时间、action、provider、session key、退出码、耗时、变更路径、校验状态和已脱敏错误类别。日志不记录 prompt 全文、认证信息、`.env` 内容或外部模型原始隐藏推理。交接包仅包含完成本轮所需的背景与允许文件。

## 9. 能力探测

`probe_capabilities.py` 用 ephemeral session 在 gitignored 的 `capability-lab/` 运行最小新建文件实验，记录原生 `Write` 与精确 Bash 创建兜底是否实际成功。它在首次需要创建文件/目录、记录超过七天、CLI/profile 变化、或工具缺失失败后运行；不在每次任务前运行。探测更新 `.ai-collaboration/provider-capabilities.json`，而不是让模型自行改写 Skill 的安全规则。探测结论只描述新 session；持续 session 同时保存其创建时的 `initial_toolset`，以避免把新工具错误地假定为旧会话可用。

## 10. 主题生命周期

每个新 persistent session 同步登记到 `topics.json`，包括 topic、provider、profile、working directory、session key/ID 和可选父 session。`--fork-session` 由 Claude Code 的真实 `--resume … --fork-session` 组合实现，子 session 不覆盖父 session。`archive_session.py --session-key <key>` 将 session 标为 archived，并在 `.ai-collaboration/archives/` 写入可供下一位协作者读取的非敏感索引；归档时不复制 token 或 `.env` 片段。

## 11. 一次性独立审查

`review_execution.py --run-id <id>` 只接受已 completed 的 execute 输出，要求显式选择另一 provider（也可明确指定），生成仅含变更路径和 outcomes 摘要的 read-only handoff，并把 critique 原始结果封存到 `reviews/`。该流程没有“审查者再通知执行者”的自动步骤，因此不会形成递归或自动辩论。

2026-07-28 的实测：MiMo 与 DeepSeek 的新 ephemeral session 均成功使用原生 `Write` 新建文件。首条 MiMo 长会话在 `Write` 被加入执行器之前创建，因此恢复后只具有 `Read,Glob,Grep,Edit`；其精确 `touch` 白名单兜底已验证成功。这是一次通用的 session 工具集陈旧样本，不是 MiMo 专属路由规则；任何 provider 的旧 session 都按同一机制处理。

## 12. 协作效能与最小持久化（P0 已实现；P1/P2 待实施）

实施以 `docs/专题/2026-07-29-协作效能优化/方案.md` 为设计输入，并以专题入口记录的状态和证据校验进展。P0 已为 `collaborate.py` 增加 `return_mode`：默认 `compact` 将 stdout 限制为最多 8 KiB 的 envelope；`structured` 只接受受限 response schema；`file_only` 返回索引和完整 record 的 hash；`debug` 才返回完整 record。完整 CLI JSON 始终写入 ignored runtime output，默认不打印回 Codex。response contract 不合格时记录 `result_contract_failed`，但 execute 是否完成仍由 machine outcomes、范围检查与验证命令判定。默认回传中的常见 token 形态会脱敏。

P0 的 bootstrap 会创建但不覆盖 `project-context.md`、`decisions.md` 和 `topics/`。每个非 ephemeral run 只写入对应主题的一页状态：目标、范围、状态、下一步、证据路径和 stop rule；不保存完整 handoff、模型推理、聊天或 provider output。`sessions.json` 是本机 provider/session 映射，整个 `.ai-collaboration/` 均为 ignored local state。完整 handoff、output、日志、快照和 capability 实验为带保留期的 runtime cache，默认不读入后续交接或 Codex 上下文。

P1 已实现本地 batch 控制面：`batch.py plan` 扫描非敏感文本、生成 manifest、小样本与按文件数/字节数分片；`batch.py reduce` 校验 JSONL 的路径/hash/schema、拒绝未知或重复行，并输出 pending、异常、抽样和 summary。所有 batch 状态只允许写入 ignored `.ai-collaboration/`。受控外部只读 worker 的自动接入仍待完成；不允许单次 execute 覆盖超过快照上限的根目录。P2 仍需以 Codex-only 对照校准路由、复核和预算。

## 13. 文档治理

四份主文档是当前有效规范，持续更新。实质决策以 `docs/决策记录/DEC-YYYYMMDD-<slug>.md` 版本化，记录取舍和影响范围；`docs/迭代记录.md` 记录实际变更和验证。Git 历史是逐字回溯来源，主文档版本号只用于里程碑、对外契约/schema 变更或基线冻结。

专题材料放在 `docs/专题/YYYY-MM-DD-<slug>/`，以 `README.md` 作为元数据和导航入口。入口保存不可变的讨论基线及可变的实施状态；方案、调研和验收附件只在该目录内存放。实现结论进入主文档，已完成或被取代的专题在入口注明最终状态和替代关系，不通过移动或删除材料来掩盖历史。
