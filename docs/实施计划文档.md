# 外部代理持续协作 Skill：完整实施计划

## 1. 目标与完成定义

本计划的目标不是维持一个“可调用 Claude Code 的脚本”，而是完成可演进的 headless 协作系统：Codex 作为统一入口，按任务价值决定直接处理、原生工具或已验证的外部 harness；每个协作者保持独立、可恢复的持续主题会话；在共享工作材料中积累认知；自动选择合适的执行、审查或直接处理路径；并对外部文件修改施加可验证的边界。当前 Claude Code + DeepSeek/MiMo 是已实现路径，Antigravity CLI 是后续独立 harness。调用设计以 [headless CLI 参考基线](headless-cli-references/README.md) 为重要输入。

以下全部满足才可称为完成：

1. 全局可发现的 Skill 能先依据明确的复杂仓库任务信号被选中；随后 Codex 再基于任务类型、工作模式、风险、时效性、工具依赖和会话连续性，决定直接处理、调用原生工具或交接外部协作者。
2. 新主题在健康 provider 间公平轮换；同一健康持续主题恢复正确协作者；不同主题、provider、模型 profile 和工作目录不串线。
3. 代码、文档、研究、创作、规划、数据和本地文件操作都有明确的委派边界与验收方式。
4. 外部协作者可在受控范围内读、写、运行必要命令，并能由执行器证明预期结果实际发生。
5. 一个协作者执行、另一协作者审查或生成候选的协作模式可按风险和价值启用，而不会形成递归辩论。
6. 会话、能力、路由指标、决策、当前状态和交接记录均可追溯；任何长期规则不只存在于 transcript。
7. 每项变更在设计、实现和验收时同时覆盖 macOS 与 Windows，或记录经核验的不受影响理由。

## 2. 已验证基线

以下能力已实现并完成真实 provider 验证，不重复建设：

- 项目级 `external-agent-collaboration` Skill 及隐式触发元数据。
- MiMo 与 DeepSeek 的独立 `CLAUDE_CONFIG_DIR`、本地 profile 与真实 API 调用。
- Claude Code `-p`、JSON 结果、显式 `--resume` 和 ephemeral 会话。
- 允许路径、敏感路径、命令白名单、快照、越界修改恢复和审计日志。
- 两家 provider 的创建 session、恢复 session、受控编辑和新 session `Write` 能力探测。
- provider 新 session 能力档案与持续 session `initial_toolset` 的分离记录。

这些能力仍须纳入后续回归测试；“已验证”不等于以后不会因 CLI、模型或 profile 变化而回退。

## 3. 未完成能力与实施工作包

### WP-1：确定性委派决策与任务分类

实现 `classify_task` 层，输入当前用户请求、项目状态、相关文件规模和已知会话，输出：

```json
{
  "task_type": "code | document | research | creative | planning | data | file_operations | personal_advice | current_information",
  "mode": "analyze | draft | critique | revise | execute | verify",
  "risk": "low | medium | high | prohibited",
  "context_size": "small | medium | large",
  "tool_requirement": "none | read_only | file_edit | shell | native_codex",
  "delegation": "direct | native_codex | external_agent",
  "reason": "..."
}
```

先由 `SKILL.md` 的元数据完成 Skill 发现：恢复协作主题、明确要求独立/第二模型评审、全仓/关联模块/多文件任务或边界明确的独立实施是主动选中信号；简单问答、常规评审和小型单文件修改是排除信号。选中后，才将此分类作为每次可能委派前的必经步骤。对当前信息、连接器数据、图像/表格/幻灯片/PDF 成品和简单对话，强制选择 Codex 原生路径。对敏感或禁止内容，强制拒绝交接。敏感性规则必须识别真实凭据/私有数据的形态与上下文，不能仅因架构文档或脱敏约束中出现“token”“secret”“credential”等词而误判为禁止；误判时保留本地处理或要求脱敏，而非绕过安全门外发。

完成条件：用例覆盖所有 task type；同一输入可解释地得到同一决策；不发生“简单改写自动外包”“实时研究交给 CLI 记忆回答”，或“仅含敏感词的安全政策文本被误判为真实敏感数据”。

### WP-2：公平 provider 路由、可用性状态与表现档案

实现 `.ai-collaboration/provider-metrics.json` 与 `record_outcome`：每次外部调用记录 provider、模型 profile、task type、mode、风险、耗时、成本、工具拒绝、是否一次完成、返工次数、Codex 质量评分和用户采纳结果。

路由优先级：用户指定 > 健康的精确主题 session > 健康候选的持久化公平轮换。当前所有外部可委派文本和限定范围代码任务均按 `task_type:mode` 轮换；表现指标保留作审计和未来显式启用学习路由的输入，不得根据厂商宣传或 provider 名称硬编码偏好。新增本地 `provider-health.json`：余额/认证/端点/配置问题冷却 24 小时，限流/传输/服务端问题以 5 分钟、15 分钟、1 小时、6 小时退避；仅可用性故障允许一次自动跨 provider 兜底。

完成条件：新主题不再按 session 数量或评分选择；能展示每次选择依据和脱敏 health 摘要；指标和 health 不会记录 token、提示词全文、原始 stderr 或敏感文件内容。

### WP-3：主题、workspace 与会话生命周期

实现主题注册表和显式会话动作：`consult`、`continue`、`draft`、`critique`、`execute`、`handoff`、`fork`、`archive`。

- 一个持续主题绑定 provider、profile、工作目录、session ID、父 session（如有）、状态和摘要。
- 实现 Claude CLI `--fork-session`：需要新工具集或分支方案时 fork，保留父会话追溯。
- 实现 session 关闭/归档：任务结束时将关键结论、未决事项和产物索引写入 `.ai-collaboration/`，而不是长期依赖 transcript。
- 新建主题时创建最小 `project-context`、`current-state`、`decisions` 与输出索引；匹配失败或多候选时要求 Codex 明确选择，不猜测最近会话。

完成条件：任何 session 都可定位所属主题和父子关系；fork 的新 ID 被注册；归档后可仅凭共享文件重建交接包。

### WP-4：执行器完成性、工具能力与安全闭环

修复“模型回复完成但目标文件未产生仍标记 completed”的缺口。执行器接受可机器验证的 expected outcome，例如目标文件存在、文件包含指定片段、测试命令退出码为 0、JSON Schema 满足、变更数量范围。

实现顺序：

1. 在 handoff schema 中加入 `expected_outcomes` 与 `validation_commands`。
2. 由执行器而非模型文本检查 outcome；失败标记 `failed` 或 `needs_review`。
3. 新建文件/目录前检查 provider capability 与 session initial toolset；旧 session 缺工具时使用精确 Bash 白名单，或按 WP-3 fork。
4. capability probe 在首次需要能力、七天过期、CLI/profile 指纹变化、工具拒绝或连续失败后运行；加入每 provider 每日上限与失败退避。
5. 对路径、命令、删除、二进制文件、大快照和符号链接增加明确策略与测试。

完成条件：所有 execute 任务均有至少一个机器可检查 outcome；模型自述不能单独决定成功；越界、未产出、验证失败和超时都可复现且正确回滚/标记。

### WP-5：协作者组合与审查策略

实现非递归的协作编排：

- 低风险草稿：单协作者结果可直接交由 Codex 整合或呈现。
- 中风险执行：一个协作者执行，Codex 检查范围和规定验证。
- 高风险代码、架构、事实研究：执行者完成后，Codex 可请求另一 provider 做一次只读 critique；原执行者不会自动再回应，除非用户或 Codex 发起一个新的明确步骤。
- 创作与方案：可让两家各生成一个候选，由 Codex 保留差异、比较和选择，不假装存在客观唯一答案。

完成条件：每个协作图最多一层执行/审查；日志能关联父任务、执行 provider 与审查 provider；不会产生递归调用、自动争论或无限重试。

### WP-6：知识工作与原生 Codex 工具边界

为 document、research、creative、planning、data 和 personal advice 定义输入、交接、输出和验证模板：

- 文档：允许本地纯文本分析、起草、批评和修订；最终 `.docx`、表格、演示、PDF 和图像由相应原生 Skill 制作。
- 研究：先由 Codex 获取当前来源；外部协作者仅分析提供的来源或本地材料，并区分事实与推断。
- 创作：用于发散候选和独立 critique；记录用户采纳结果作为质量指标。
- 个人建议：仅在长本地资料、复杂方案或用户明确要求第二意见时委派。

完成条件：每种 task type 有一个成功、一个不应委派、一个敏感/时效边界用例；Skill 不将 CLI 协作者错误用于连接器或原生成品。

### WP-7：可观测性、维护与文档一致性

建立以下稳定记录：

- `provider-metrics.json`：路由与结果指标。
- `topics.json`：主题、session、fork、归档和产物索引。
- `provider-capabilities.json`：带 profile/CLI 指纹与有效期的实测能力。
- `docs/迭代记录.md`：每次策略、schema、CLI/profile 兼容性或测试结论变化。

每次修改脚本、Skill、路由规则或 profile schema 时，必须同步更新 PRD、技术方案、实施计划、测试用例和迭代记录；每次真实 provider 验证将结果摘要写入迭代记录，不写 token。

完成条件：文档不会把“设计目标”写成“已实现”；任何自动路由或安全决策均能追溯到状态记录或源码。

### WP-10：Windows 跨平台兼容性优化

#### 目标、边界与现状

目标是在不依赖 WSL、Git Bash 或 macOS 工具的前提下，使**同一套同步的 Skill**可在 Windows 和 macOS 上完成配置诊断、分类、路由、会话管理、结果校验和受控执行。provider 可使用一份通用 local 配置，或使用独立的 macOS/Windows Git 忽略配置文件；token 默认直接由用户写入这些配置文件。用户自行决定是否使用私有同步机制同步配置文件，Skill 不要求任何 OS 凭据库或环境变量。Windows 不复用 macOS 的 CLI session 与能力探测，但两端可复用 provider 定义、端点/模型映射与主题状态。

2026-07-29 的 Windows 基线测试显示：13 个本地回归脚本中 11 个通过；`test_outcomes.py` 因 Unix `true` 命令失败，`test_provider_health.py` 因 POSIX 工作目录与 Windows 规范路径不相等而失败。现有 profile 的 macOS 配置目录无法通过 `doctor.py`；Keychain 分支直接调用 `security`；能力探测的 Bash 兜底使用 `mkdir -p` 与 `touch`。这些结论是本工作包的验收基线，不应通过安装兼容层来掩盖。

本工作包不包括：自动复制或猜测用户的 macOS 凭据、把现有 macOS session ID 强行恢复到 Windows、自动安装全局依赖、或在迁移过程中发起真实 provider 调用。

#### WP-10.1：平台抽象与安全命令模型

1. 新增单一平台适配层，集中提供主机平台、可执行文件后缀、路径显示、配置目录校验和本地验证命令执行；业务脚本不得散落调用 `security`、`touch`、`mkdir -p` 或依赖默认 shell。
2. 将 `command_succeeds` 从自由字符串逐步迁移为结构化、无 shell 的 `argv` 命令；执行器使用 `subprocess.run(argv, shell=False)`，并以规范化的参数数组做白名单匹配。需要 shell 的项目测试必须显式声明 shell 类型和完整命令，不得由运行器推断。
3. 将“创建文件的 Bash 兜底”改为 fail-closed 的策略：优先原生 `Write`；恢复 session 缺 `Write` 时 fork 或新建 session；未确认实际 shell 类型时不生成跨平台创建命令。后续若保留 shell 兜底，必须将 `shell_kind`、命令模板和实测结果写入 capability 记录。
4. 将测试中的成功空命令改为使用当前 Python 解释器的无副作用命令，禁止继续依赖 `true`、`touch`、`chmod` 等仅在部分平台存在的程序。

完成条件：Windows、macOS 上的同一非 shell outcome 使用相同的 `argv` 结构通过；Windows 默认命令解释器下不出现 Unix 命令未找到；未识别 shell 时执行器拒绝而不是降级执行。

#### WP-10.2：用户管理的配置文件与平台 local profile

1. 将 Git 忽略的配置文件确立为唯一默认凭据载体。支持通用 `providers.local.json`，以及覆盖优先级更高的 `providers.local.macos.json`、`providers.local.windows.json` 和 `providers.local.posix.json`；平台文件可直接保存 `auth_token`、launcher 和绝对 `config_dir`。
2. 可选的版本化 `providers.shared.json` 只保存不含 token 的 provider 定义、端点/模型映射和相对主目录目录名；运行时按“shared → 当前平台 override → 通用 local → 当前平台 local”合并。用户可选择以自己的私有同步方案同步任意 Git 忽略配置文件，Skill 不得假定或阻止这种同步。
3. 不要求、推荐或自动迁移到环境变量、macOS Keychain、Windows Credential Manager 或其他系统凭据库。已有直接 `auth_token` 的 profile 是有效且受支持的配置；迁移工具如存在，只能在 Git 忽略的平台 local 配置文件间复制 token，且不得输出其值。
4. `bootstrap.py` 在 Windows 上使用可验证的用户目录权限检查或清晰的“无法自动收紧 ACL”提示；不得把 POSIX `chmod` 成功当作 Windows 私密性证据。
5. profile 的有效配置（合并后端点、模型映射、配置目录、认证方式、当前平台与 launcher 指纹）变更都必须使信任指纹失效；维护者已授权的后续实施自动建立或刷新当前非密钥 trust record。

完成条件：macOS 与 Windows 可各自使用直接 token 的 Git 忽略配置文件；`doctor.py --json` 在两端仅输出脱敏、可操作的问题列表；不存在“必须使用环境变量或 OS 凭据库”的前置条件；token 不会进入 Git、handoff、输出、日志、测试 fixture 或外部提示词。

#### WP-10.3：工作目录、会话与能力记录迁移

1. 将运行态 schema 升级为带 `host_platform`、规范化 `working_directory` 和 `workspace_identity` 的版本。`workspace_identity` 只用于本机项目匹配，不能包含凭据或完整用户目录。
2. 旧记录迁移采用“识别、报告、重新建会话”的保守方案：不同平台或无法验证的工作目录记录标记为 `incompatible_platform` 或归档；保留 topic、证据索引和原 session ID，但绝不自动路径替换或 `--resume`。
3. 新 Windows session 以当前 Windows 规范路径和独立 provider profile 创建；持续 topic 通过一页 topic state 衔接上下文，而不是迁移 CLI session 身份。
4. `provider-capabilities.json` 增加平台、launcher 指纹和 shell 证据。来自 macOS 的能力探测在 Windows 一律过期，首次 Windows execute 前必须重新探测。
5. 提供只读 `--dry-run` 迁移报告，以及需用户显式触发的本地 `--apply`；应用前备份 ignored runtime state，失败时保留原记录不覆盖。

完成条件：POSIX session 路径不会被 Windows 路由误匹配；跨平台记录不会触发 `--resume`；Windows 首次 execute 不会复用 macOS capability 结论；迁移报告不含认证值或完整 provider 输出。

#### WP-10.4：测试、持续集成与发布门槛

1. 为路径规范化、foreign-session 拒绝、platform-local profile 诊断、结构化 outcome、能力记录失效和 Windows launcher 增加独立本地回归。
2. 新增共享配置回归：同一 portable profile 必须在模拟 Darwin/Windows 主目录下解析出各自正确的 `config_dir`；`claude` 必须经当前平台 PATH 解析；任何共享 profile 出现 `auth_token`、绝对用户目录或固定 `.exe` launcher 均应被静态检查拒绝。
3. 重写现有 provider-health fixture，使用临时目录的实际规范路径，而不是硬编码 `/project`；重写 outcome fixture，使其使用当前 Python 解释器的跨平台成功命令。
4. Windows 回归必须覆盖 `cmd.exe` 与 PowerShell 可执行验证路径；macOS 回归保留 POSIX 路径和既有 native Write 行为。两端均执行 fake launcher；已配置且已信任的本机 profile 直接执行最小真实 smoke。
5. 在 CI 中新增 Windows 与 macOS 任务，最低覆盖所有 `test_*.py`、Python 语法解析、`bootstrap --check`、共享 profile schema 校验和解析快照。因受限目录无法写入 `__pycache__` 时，语法检查必须使用不写入源码树的方式，不能以 ACL 失败掩盖语法结果。
6. 先以双平台本机控制面和共享配置回归全部通过为发布门槛；之后在两端以已配置、已信任 profile 的最小无敏感只读 smoke 验证 launcher 和 profile，不在 CI 中使用真实认证。

完成条件：所有本地回归在 Windows 和 macOS 通过；Windows 与 macOS CI 均为必需检查；一份共享 profile 的双端解析快照一致且不含凭据；真实 provider 验证仅证明已配置的本机 profile 可用，不替代跨平台单元测试。

#### 分阶段交付、回滚与风险控制

|阶段|交付内容|阻断条件|回滚方式|
|---|---|---|---|
|P0：控制面修复|平台适配层、结构化本地验证、Unix 测试替换、明确的非 Darwin 诊断。|任何 Windows 本地回归失败。|保持旧 schema 与旧 runner，仅发布测试和适配分支。|
|P1：运行态隔离|session/capability schema 升级、foreign-session 拒绝、dry-run 迁移报告。|迁移报告不能区分本机与外来记录。|不执行 apply；保留旧 ignored runtime 备份。|
|P2：双平台配置启用|通用/平台 local profile 合并、直接 token 配置、双端诊断、信任指纹重建、最小 fake launcher 验证。|诊断不脱敏、token 泄漏到 Git/handoff/output/log，或 profile 不能明确失败。|恢复用户管理的本机配置备份；移除本地 trust record。|
|P3：受控真实验证|已配置且已信任 profile 的最小真实 smoke、Windows CI 必需检查、文档和迭代记录同步。|任何真实调用产生范围外变更或 outcome 失败。|停止该路径的 provider 调用，归档失败证据并回退到 P2 本地验证。|

主要风险是错误地把两个不同平台上的目录或 session 视为同一工作区、在 Windows 上误执行 Unix shell 命令、以及迁移时误处理本地认证。所有风险均按“无法确认即拒绝”的原则处理；不以便利性换取 session 连续性或认证自动化。

### WP-11：Headless multi-harness 与 Antigravity CLI

本工作包不把 Antigravity 视为第三个 Claude Code provider，而是建立可替换的 harness adapter 边界。其事实与限制以 [官方参考转换稿](headless-cli-references/README.md) 为输入；任何具体 flag 都须在实现时以本机 `--help` 和双平台测试复核。

#### WP-11.0：敏感性 gate 精确化（P0 前置）

1. 替换当前“出现 `token`/`secret`/`password` 等任意词即禁止”的 substring 规则。高置信度禁止仅匹配实际凭据值/赋值、私钥块、明确的 `.env` 内容、客户/生产数据正文或用户要求外发这些内容的语境。
2. 增加 `requires_redaction`：疑似但无法确定的真实敏感内容先要求移除或置换，再重新分类；“不要发送 token”“本系统禁止读取 `.env`”等政策性、否定性或文档性文字不能直接成为 `prohibited`。
3. 在 provider 调用前保留独立的最终 handoff/file scanner。分类器通过不是外发许可；任何最终材料的高置信度秘密仍阻断调用并给出不回显值的定位类别。

完成条件：真实秘密值仍被拒绝；仅讨论安全政策、认证方案或 redaction 规则的架构 handoff 可按普通任务分类；macOS/Windows 上的正则、文件路径与 `.env` 检测结果一致。

#### WP-11.1：Claude Code adapter 与原生结构化输出（P0）

1. 将现有 CLI 拼装、JSON 解析、`permission_denials` 处理和 session resume 迁入 `ClaudeCodeAdapter`，输出统一 envelope；不得改变 DeepSeek/MiMo profile、公平 provider 轮换、`dontAsk` 或“不传 runner-level `--model`”。
2. 将 runner response contract 编译为 Claude CLI JSON Schema，传入 `--json-schema` 并优先消费 `structured_output`；保留当前 JSON 文本解析作为版本兼容回退。为“handoff 与 runner contract 冲突”“JSON 外附文本”“schema 无效”“旧 CLI 无字段”写明确定结果。
3. 引入只在用户/调试显式启用时使用的 stream diagnostics，最小化记录 API retry、permission、插件/MCP load failure 和终态；不保存 token、prompt、完整事件或子代理思考。
4. `--bare` 只作为显式、已验证的 CI/read-only profile 选项；默认禁用，避免跳过隔离 profile 所需 plugin、skill、MCP 或配置。

完成条件：现有 Claude fake launcher 与真实最小 smoke 均可证明 schema output、permission denial 和 session resume 正确；没有 profile mapping 或插件意外丢失；macOS、Windows 回归均通过。

#### WP-11.2：通用 adapter、状态与迁移（P1）

1. 定义 `HarnessAdapter` 的最小接口：`doctor`、`invoke`、`parse_result`、`resume`、`capabilities`、`classify_error` 和 `permission_state`。adapter 只接收脱敏 handoff 与已批准的 profile，不能读取其他 harness 的认证。
2. 将 session、trust、health、capability 和 metric key 升级为包含 `harness`、`harness_profile`、`provider/profile`、`host_platform` 和 `workspace_identity`；旧 record 显式迁移为 `claude_code`。
3. 新增 feature flag 与只读 dry-run migration。默认路由和现有 session 必须保持 Claude Code 行为；任一 migration 不得猜测 Antigravity conversation 或把 Claude ID 写入 Antigravity。

完成条件：双 harness 的 fake CLI 可并存；跨 harness resume/health/trust/capability 污染被拒绝；关闭 feature flag 后无行为回归。

实施状态：已完成 `HarnessAdapter` 协议、Claude-first record identity、legacy Claude record 的 dry-run/backup-then-apply migration，以及启用 feature flag 后 foreign session 的 fail-closed 回归。P4 已完成有限的公共只读 role router：它按 session、用户指定、handoff 敏感性、独立审查意图和当前 Antigravity readiness 选择 harness；health/trust/capability 仍不跨 harness 复用，DeepSeek/MiMo provider routing 只在 Claude Code 内运行。

#### WP-11.3：Antigravity read-only adapter（P2）

1. 在用户完成 Antigravity 的确实需要人工处理的交互式认证、安装本机 CLI 后，实现 `agy -p --output-format json --json-schema` 的 read-only `consult`/`critique`；已授权实施自动建立当前非密钥 profile 的 trust record。
2. 保存和恢复该 CLI 的 `conversation_id`，解析 `SUCCESS/ERROR/CANCELED/INTERRUPTED` 等终态、`structured_output`、stderr 和 stream events；将任何工具软拒绝（即使退出 0）归为 `blocked_by_permission`。
3. Antigravity 的 model/effort/agent 只可由固定本机 harness profile 指定并进入 fingerprint；第一版不根据任务直接传任意 model slug，也不加入 DeepSeek/MiMo 自动轮换。

完成条件：macOS 与 Windows 各有 fake CLI 回归；各自已配置、已信任的 profile 完成一项无工具、无敏感的真实 smoke；认证缺失、unknown model、soft denial、timeout 和 JSON schema error 都有无凭证的确定诊断。

实施状态：已实现 `AntigravityAdapter`、固定 `plan` 的显式 `consult_antigravity.py`、非密钥 local profile 与指纹 trust、conversation ID 存储，以及 macOS/Windows fake-launcher 分支；`stream-json` 的 terminal 解析与无内容 diagnostics 也已有回归。macOS 与 Windows 均已完成无工具、无敏感的真实 schema smoke：均为 completed，记录独立 conversation/session，且没有项目文件变化或 permission denial。P2 已完成。P3 的 macOS/Windows 主工作树诊断和两端 isolated full-auto 诊断均显示：`always-proceed` 与 `write_to_file` 可用仍不写目标，故 AGY execute 已固定不可用。P4 的 public read-only role router 与 macOS/Windows automatic smoke 均已完成；两项均不改变“AGY 只读、Claude Code 唯一自动 execute”的产品结论。

#### WP-11.4：受控 execute 与分类策略（P3/P4）

1. AGY execute 不开放；macOS/Windows 同一 disposable isolated P3 对照均已取得预期失败证据，不改变路由。此后只有未来 CLI/agent 更新并在 isolated P3 契约得到真实成功证据，才可重新评估。主工作树永不运行 AGY full-auto。
2. 分类器改为两阶段：先判定 native/direct/external，再以角色路由选择 harness。Claude Code 是“项目协作者”：持续主题、项目 execute、CC Switch profile/plugin/MCP 与一般新项目协作默认归它；Antigravity 是“独立审查者”：**仅**在任务明确要求第二方案/反方意见/风险审查，且无历史会话、只读时归它。新会话本身不触发 Antigravity；用户指定优先。
3. DeepSeek/MiMo 的公平轮换仅保留在 Claude Code project-collaborator pool 内；Antigravity 不参与公平轮换。只有形成同一基准集的证据并新增 DEC 后，才可扩大 Antigravity 的默认角色。availability failure 以外的失败永不自动跨 harness 重试。

完成条件：Antigravity execute 的任何越界、软拒绝或 outcome failure 都会停止并恢复；分类理由可审计；现有 DeepSeek/MiMo Claude Code 轮换不被改变。
