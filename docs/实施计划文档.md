# 外部代理持续协作 Skill：完整实施计划

## 1. 目标与完成定义

本计划的目标不是维持一个“可调用 Claude Code 的脚本”，而是完成五轮讨论所定义的协作系统：Codex 作为统一入口，按任务价值决定是否引入 MiMo 或 DeepSeek；每个协作者保持独立、可恢复的持续主题会话；在共享工作材料中积累认知；自动选择合适的执行、审查或直接处理路径；并对外部文件修改施加可验证的边界。

以下全部满足才可称为完成：

1. Codex 能基于任务类型、工作模式、风险、时效性、工具依赖和会话连续性，决定直接处理、调用原生工具或交接外部协作者。
2. 新主题按真实本地表现路由 已配置 provider；同一持续主题恢复正确协作者；不同主题、provider、模型 profile 和工作目录不串线。
3. 代码、文档、研究、创作、规划、数据和本地文件操作都有明确的委派边界与验收方式。
4. 外部协作者可在受控范围内读、写、运行必要命令，并能由执行器证明预期结果实际发生。
5. 一个协作者执行、另一协作者审查或生成候选的协作模式可按风险和价值启用，而不会形成递归辩论。
6. 会话、能力、路由指标、决策、当前状态和交接记录均可追溯；任何长期规则不只存在于 transcript。

## 2. 已验证基线

以下能力已实现并完成真实 provider 验证，不重复建设：

- 项目级 `external-agent-collaboration` Skill 及隐式触发元数据。
- MiMo 与 DeepSeek 的独立 `CLAUDE_CONFIG_DIR`、本地 profile 与真实 API 调用。
- Claude Code `-p`、JSON 结果、显式 `--resume` 和 ephemeral 会话。
- 允许路径、敏感路径、命令白名单、快照、越界修改恢复和审计日志。
- 两家 provider 的创建 session、恢复 session、受控编辑和新 session `Write` 能力探测。
- provider 新 session 能力档案与持续 session `initial_toolset` 的分离记录。

这些能力仍须纳入后续回归测试；“已验证”不等于以后不会因 CLI、模型或 profile 变化而回退。

## 3. 未完成能力与实施工作包

### WP-1：确定性委派决策与任务分类

实现 `classify_task` 层，输入当前用户请求、项目状态、相关文件规模和已知会话，输出：

```json
{
  "task_type": "code | document | research | creative | planning | data | file_operations | personal_advice | current_information",
  "mode": "analyze | draft | critique | revise | execute | verify",
  "risk": "low | medium | high | prohibited",
  "context_size": "small | medium | large",
  "tool_requirement": "none | read_only | file_edit | shell | native_codex",
  "delegation": "direct | native_codex | external_agent",
  "reason": "..."
}
```

在 Skill 中将此分类作为每次可能委派前的必经步骤。对当前信息、连接器数据、图像/表格/幻灯片/PDF 成品和简单对话，强制选择 Codex 原生路径。对敏感或禁止内容，强制拒绝交接。

完成条件：用例覆盖所有 task type；同一输入可解释地得到同一决策；不发生“简单改写自动外包”或“实时研究交给 CLI 记忆回答”。

### WP-2：可学习的 provider 路由与表现档案

实现 `.ai-collaboration/provider-metrics.json` 与 `record_outcome`：每次外部调用记录 provider、模型 profile、task type、mode、风险、耗时、成本、工具拒绝、是否一次完成、返工次数、Codex 质量评分和用户采纳结果。

路由优先级：用户指定 > 精确主题 session > 同类有效样本评分 > 冷启动平衡轮换。每个 task type + mode 在样本不足时轮换；达到最小样本后按质量优先、成本/速度/稳定性为次级规则；保留可配置比例的探索调用。不得根据厂商宣传硬编码“MiMo 擅长 X / DeepSeek 擅长 Y”。

完成条件：新主题不再按 session 数量选择；能展示每次选择依据；指标不会记录 token、提示词全文或敏感文件内容。

### WP-3：主题、workspace 与会话生命周期

实现主题注册表和显式会话动作：`consult`、`continue`、`draft`、`critique`、`execute`、`handoff`、`fork`、`archive`。

- 一个持续主题绑定 provider、profile、工作目录、session ID、父 session（如有）、状态和摘要。
- 实现 Claude CLI `--fork-session`：需要新工具集或分支方案时 fork，保留父会话追溯。
- 实现 session 关闭/归档：任务结束时将关键结论、未决事项和产物索引写入 `.ai-collaboration/`，而不是长期依赖 transcript。
- 新建主题时创建最小 `project-context`、`current-state`、`decisions` 与输出索引；匹配失败或多候选时要求 Codex 明确选择，不猜测最近会话。

完成条件：任何 session 都可定位所属主题和父子关系；fork 的新 ID 被注册；归档后可仅凭共享文件重建交接包。

### WP-4：执行器完成性、工具能力与安全闭环

修复“模型回复完成但目标文件未产生仍标记 completed”的缺口。执行器接受可机器验证的 expected outcome，例如目标文件存在、文件包含指定片段、测试命令退出码为 0、JSON Schema 满足、变更数量范围。

实现顺序：

1. 在 handoff schema 中加入 `expected_outcomes` 与 `validation_commands`。
2. 由执行器而非模型文本检查 outcome；失败标记 `failed` 或 `needs_review`。
3. 新建文件/目录前检查 provider capability 与 session initial toolset；旧 session 缺工具时使用精确 Bash 白名单，或按 WP-3 fork。
4. capability probe 在首次需要能力、七天过期、CLI/profile 指纹变化、工具拒绝或连续失败后运行；加入每 provider 每日上限与失败退避。
5. 对路径、命令、删除、二进制文件、大快照和符号链接增加明确策略与测试。

完成条件：所有 execute 任务均有至少一个机器可检查 outcome；模型自述不能单独决定成功；越界、未产出、验证失败和超时都可复现且正确回滚/标记。

### WP-5：协作者组合与审查策略

实现非递归的协作编排：

- 低风险草稿：单协作者结果可直接交由 Codex 整合或呈现。
- 中风险执行：一个协作者执行，Codex 检查范围和规定验证。
- 高风险代码、架构、事实研究：执行者完成后，Codex 可请求另一 provider 做一次只读 critique；原执行者不会自动再回应，除非用户或 Codex 发起一个新的明确步骤。
- 创作与方案：可让两家各生成一个候选，由 Codex 保留差异、比较和选择，不假装存在客观唯一答案。

完成条件：每个协作图最多一层执行/审查；日志能关联父任务、执行 provider 与审查 provider；不会产生递归调用、自动争论或无限重试。

### WP-6：知识工作与原生 Codex 工具边界

为 document、research、creative、planning、data 和 personal advice 定义输入、交接、输出和验证模板：

- 文档：允许本地纯文本分析、起草、批评和修订；最终 `.docx`、表格、演示、PDF 和图像由相应原生 Skill 制作。
- 研究：先由 Codex 获取当前来源；外部协作者仅分析提供的来源或本地材料，并区分事实与推断。
- 创作：用于发散候选和独立 critique；记录用户采纳结果作为质量指标。
- 个人建议：仅在长本地资料、复杂方案或用户明确要求第二意见时委派。

完成条件：每种 task type 有一个成功、一个不应委派、一个敏感/时效边界用例；Skill 不将 CLI 协作者错误用于连接器或原生成品。

### WP-7：可观测性、维护与文档一致性

建立以下稳定记录：

- `provider-metrics.json`：路由与结果指标。
- `topics.json`：主题、session、fork、归档和产物索引。
- `provider-capabilities.json`：带 profile/CLI 指纹与有效期的实测能力。
- `docs/迭代记录.md`：每次策略、schema、CLI/profile 兼容性或测试结论变化。

每次修改脚本、Skill、路由规则或 profile schema 时，必须同步更新 PRD、技术方案、实施计划、测试用例和迭代记录；每次真实 provider 验证将结果摘要写入迭代记录，不写 token。

完成条件：文档不会把“设计目标”写成“已实现”；任何自动路由或安全决策均能追溯到状态记录或源码。

### WP-8：协作效能优化

以 `docs/专题/2026-07-29-协作效能优化/README.md` 的状态和[方案](专题/2026-07-29-协作效能优化/方案.md)为准，将 token、质量、总成本和完成效率作为同一协作决策的约束。P0 已完成本地实现、回归和一次已配置 provider 的只读 smoke：紧凑且可验证的回传、最小协作持久化与一页主题状态。P1 再实现以小样本和抽样验收为前提的 batch，P2 最后用 Codex-only 对照结果校准路由、复核和预算。在 P1 完成前，不自动将大批材料任务扩大到外部协作。

完成条件：Codex 默认不接收完整 provider result；大批任务可断点恢复、按需读取并通过抽样/结构化验收；协作路径在同等质量下能解释其总成本和效率收益。


### WP-9：文档治理与决策可追溯

将四份主文档维护为当前有效规范；建立 `docs/决策记录/`，为重大取舍、兼容性变化、schema/interface 变化和被废止决定创建带 ID 的短决策记录；将有讨论基线与实施周期的优化纳入 `docs/专题/YYYY-MM-DD-<slug>/`，由专题入口维护基线、状态、主文档映射和证据；迭代记录只记录实际变更与验证。

完成条件：新增优化需求能定位其专题入口、讨论基线、决策记录、受影响主文档、实现/测试证据和迁移说明；不会通过复制整份 PRD/技术方案制造多份相互冲突的“当前版本”，也不会在 `docs/` 顶层遗留失去状态的专题文件。

## 4. 集成顺序与依赖

1. 先完成 WP-4 的 outcome schema 与执行器正确性，再扩大自动 execute 的覆盖面。
2. 完成 WP-1 分类模型和 WP-2 指标 schema，再替换现有按 session 数量的冷启动路由。
3. 完成 WP-3 fork/归档与 topics registry，使自动分类有可靠的会话目标。
4. 完成 WP-5 协作编排，避免在路由和 session 未稳定时引入第二协作者。
5. 完成 WP-6 模板和原生工具边界，覆盖非代码任务。
6. WP-7 贯穿所有工作包；每次合入都同步记录和回归。

## 5. 验收矩阵

|能力|必测证据|
|---|---|
|委派分类|每种 task type/mode 的直接、原生、外部和禁止样例。|
|学习路由|冷启动轮换、样本充分后的选择、探索比例、用户指定覆盖。|
|会话连续性|创建、精确恢复、fork、归档和多候选拒绝。|
|文件执行|允许路径修改、新建、删除、越界恢复、未达 outcome、测试失败。|
|能力探测|新 session、旧 session、CLI/profile 变化、过期、退避与不重复调用。|
|双协作者模式|执行+一次 critique、双候选、禁止递归。|
|非代码边界|文档、研究、创作、数据、生活建议、实时信息和原生成品。|
|安全与审计|无 token 泄漏、无全局 CC Switch 切换、日志/文档可追溯。|

## 6. 当前状态与下一步

当前处于“核心 harness、WP-1/WP-2 和 WP-3 主路径已实现，完整协作系统仍待建设”的状态。已落地：handoff outcomes schema、执行器机器判定、失败回滚、受控验证命令、结构化任务分类、匿名表现路由、cold-start 轮换、topic 自动登记、真实 CLI session fork 与 archive。execute 创建新文件时会自动复用/更新能力探测，并在旧 session 缺 Write 时自动 fork。
