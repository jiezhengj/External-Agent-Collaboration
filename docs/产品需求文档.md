# 外部代理持续协作 Skill：产品需求文档

## 1. 背景与目标

本项目要在 Codex 桌面端中提供一个项目级 Skill，使 Codex 能把适合的工作自动交接给本地配置的 headless CLI 协作 harness，并在后续请求中恢复同一协作主题的会话。Claude Code 是当前唯一自动 execute harness；Antigravity CLI 是独立的、已验证只读协作 harness，只能承担定义好的独立评审角色，尚未进入项目 execute 路由。

这不是一次性子代理，也不是多代理自动辩论。Codex 是用户的统一入口与协调者；本地配置的外部 provider 是各自保有项目会话的协作代理。每次外部调用对应用户请求或 Codex 的一次明确协作步骤，结果回到 Codex 后再继续对话。

首版必须同时具备：

- 自动判断何时调用外部协作者；
- 自动选择或恢复正确的协作者会话；
- 对授权任务允许外部代理修改项目文件；
- 保存可读、可恢复的协作状态；
- 对高风险行为保留机械约束与可审计记录。

## Execute 权限编排需求

系统必须按任务工具需求选择可审计 profile：Claude Code 默认 `acceptEdits` 并只为已知命令补充精确 `allowedTools`。AGY 的 `readonly`、`controlled-execute` 与 `local-full-auto` profile 仅保留为诊断和未来版本复验的隔离实验配置；当前 AGY headless execute 未通过目标写入实验，不进入项目 execute 路由。即使未来重验 `local-full-auto`，`--dangerously-skip-permissions` 也只能在 disposable isolated executor 中使用，并仍受目标、outcome 和回滚契约约束。

## 2. 用户与场景

|场景|期望行为|
|---|---|
|延续一个品牌、写作或技术主题|匹配主题、供应商、模型配置与工作目录，恢复准确 session。|
|陌生项目或大量本地资料分析|自动建立会话、交接限定资料，输出结构化结论。|
|需要实际落地的代码、文档或文件改动|外部代理在授权范围内修改；Codex 读取变更、运行规定校验并向用户说明。|
|需要另一种观点|保留协作者的独立产出，不强制再让其他代理自动反驳。|
|时效信息、连接器数据或原生成品|优先 Codex 的网页、连接器、图像、文档、表格等原生能力，不调用 CLI 协作者。|

## 3. 范围

### 3.1 包含

- 项目级 `external-agent-collaboration` Skill。
- 可配置 provider 的确定性启动 profile。
- `consult`、`continue`、`draft`、`critique`、`execute` 五类动作。
- 按持续主题管理的 Claude Code session ID。
- 交接包、输出、会话记录、执行日志和变更快照。
- 自动委派、自动恢复、自动输出归档；一次调用完成后返回 Codex。
- 外部代理在显式授权的任务范围内读取、编辑文件和运行有限命令。

### 3.2 不包含

- 自动修改 CC Switch 的全局当前供应商。
- 在不同 provider profile 之间复用同一 Claude Code session。
- 外部代理提交、推送、部署、发布、改写 Git 历史、安装全局包或读取密钥。
- 无用户请求或无 Codex 决策触发的后台循环、自动辩论或递归代理调用。
- 将完整 Codex 聊天记录、ChatGPT Memory、连接器数据或不相关文件发送给外部模型。

## 4. 核心需求

### R1：Skill 发现与自动协作决策

Skill 隐式调用保持开启，但先区分“选中 Skill”与“实际委派”。全局可发现时，`SKILL.md` 的触发元数据应在下列任一信号明确出现时主动选中：已有主题会话可延续；用户需要独立或第二模型评审；请求覆盖整个仓库、关联模块或多个文件；需要边界明确的独立实施；或外部协作者的既有主题认知会显著降低交接成本。选中后，再由任务分类、可用 provider 配置和安全检查决定是否实际调用外部协作者。

不应选中或委派的任务必须由 Codex 直接处理或使用原生工具：简单问答/改写、常规评审、小型单文件修改、实时事实未核验的研究、连接器私有数据、图像或办公成品制作，以及敏感内容。

### R2：会话连续性

每条会话绑定 `topic + provider + model_profile + working_directory + initial_toolset`。首次调用保存 CLI 返回的 `session_id` 与创建时工具集；同主题后续调用只能使用 `--resume <session_id>`。主题明显变更、模型配置变更或供应商变更时创建新会话；分支方案使用 fork，而非污染原会话。

### R3：确定性供应商启动

每个供应商由独立 launcher 和独立 `CLAUDE_CONFIG_DIR` 启动。Skill 不得通过切换 CC Switch 全局状态选择模型。项目的默认且用户可控的凭据载体是 Git 忽略的本地配置文件：可使用通用 `.ai-collaboration/providers.local.json`，也可分别使用 `providers.local.macos.json` 与 `providers.local.windows.json`。token 可直接写在对应配置文件中；是否由用户的私有同步机制同步这些文件由用户决定。Skill 不得要求环境变量、钥匙串或其他系统凭据库；token 不得写入版本化文件、会话注册表、交接包、日志或外部提示词。

### R4：受控外部修改

`execute` 可由 Skill 自动选择，但仅在任务明确需要落地且工作区符合条件时启用。执行前必须：确认允许目录、检查敏感路径、记录文件快照、生成最小命令白名单。执行后必须记录外部结果、变更文件、命令结果与校验结果；Codex 根据风险检查 diff、测试或输出清单。

### R5：共享协作材料

项目内 `.ai-collaboration/` 保存稳定背景、当前状态、已确认决策、交接包、输出和会话注册表。它是跨聊天和会话的恢复媒介；外部 session 只是补充，不能成为唯一事实来源。

### R6：路由规则与模型职责

用户明确指定 provider 时必须尊重。否则优先恢复健康的主题绑定供应商；新主题的外部可委派工作在健康 provider 间按 `task_type:mode` 的持久化 cursor 公平轮换。记录任务类型、动作、耗时、完成情况、返工和错误原因供审计及未来经明确决策启用的学习路由使用，但当前不以样本评分打破轮换。

Codex 只路由 provider，不路由 Flash/Base/Pro。runner 不传 `--model`；隔离的 CC Switch/Claude Code profile 自行保留 FABLE/OPUS/SONNET/HAIKU/SUBAGENT 映射。Claude Code 内部是否创建子代理属于该 provider 的内部执行，不是 Codex 的独立路由、脱敏或探测对象。

启动本机 Claude Code 与向 provider 外发 handoff 是两层不同的授权。真实调用只允许已写入 ignored `trusted-providers.local.json` 且非密钥 profile 指纹仍匹配的 provider；维护者已授权 Codex 在实施时通过本机 `trust_provider.py --approve` 直接建立或刷新该记录。profile 的 endpoint、模型映射、配置目录或非密钥环境改变会使记录失效。该项目内信任门不替代 Codex 宿主平台的最终 egress 审批。

## 5. 风险分级与完成标准

|风险|例子|处理|
|---|---|---|
|低|头脑风暴、草稿、只读分析|自动交接，保留结果。|
|中|本地文档重写、普通代码修改|允许 execute；执行前快照，执行后检查范围与规定校验。|
|高|安全、架构决策、公共 API、迁移|可自动咨询或执行，但 Codex 必须验证关键结论、完整变更与相关测试。|
|禁止|密钥、生产数据、部署、Git 历史|Skill 直接拒绝外部交接或降级为不含敏感内容的协作。|

一次协作完成的标准：交接包可追溯、session/profile 可定位、输出或修改落盘、所需校验有结果、失败原因可见、Codex 向用户说明协作者贡献和未解决风险。

## 6. 验收标准

1. 用户以自然语言提出连续主题、全仓/关联模块/多文件任务或独立/第二模型评审时，Skill 能依据 metadata 隐式选中；连续主题还能恢复匹配的会话。
2. 新主题自动创建注册记录；同主题不会因“最近会话”而串线。
3. 不同 provider 的 session、配置目录和日志可区分。
4. `execute` 能在允许路径内修改文件并保存前后快照；越界、敏感路径和禁止命令会被拒绝。
5. 仅当自动选择的 provider 出现余额、认证、端点、限流、传输或服务端可用性故障时，最多对另一健康供应商故障转移一次；不会无限重试，也不会因任务、契约、outcome 或越界失败切换。
6. Skill 选中后若未配置 profile，必须以明确的诊断信息停止，不猜测端点、模型名或凭证。
7. 首次需要新建文件/目录、能力记录过期、CLI/profile 变化或报告工具缺失时，Skill 运行 ephemeral 能力探测；普通任务不会重复探测。

### R7：协作效能与最小持久化

Skill 必须以可验证交付质量为中心，同时控制 Codex 上下文回流、外部调用成本、完成时间和重复阅读。外部协作者可以直接读取授权的本地材料，但 Codex 默认只接收紧凑状态、outcomes、变更/异常路径和短摘要；完整 provider 输出仅本地落盘并按需读取。

跨 Agent 长期共享的信息只包括稳定背景、已确认决策、每个活跃主题的一页短状态和本机 session 映射。项目源码、文档、数据、测试和 Git 历史是事实唯一来源；handoff、原始输出、日志和快照属于可清理 runtime cache，不得演化为第二套项目知识库。大批材料只有在可分片、可结构化验收、可抽样且 Codex 无需逐字复核时才可外部 batch。

### R8：Headless harness 演进、分类与双平台兼容

[Headless CLI reference baseline](headless-cli-references/README.md) 中的 Claude Code 与 Antigravity 官方文档是本项目调用协议的重要工程参考。它们不自动授权任何外发或功能；采用具体 flag、权限模式或输出字段前，必须核对官方原文和本机 CLI。

系统必须将 **harness**、provider、模型 profile、session、permission policy 和结构化结果分开建模。Claude Code + DeepSeek/MiMo 保持为当前已验证组合：Codex 只在该 harness 内选择 provider，隔离 profile 决定 Flash/Pro 等内部映射。Antigravity CLI 作为独立 harness 规划：它有自己的本机认证、conversation ID、权限语义和可选 model/effort/agent 设定，不能复用 Claude Code session、信任 fingerprint 或 provider health 记录。

分类器先决定 Codex 原生处理还是外部协作；外部协作再按“已有匹配会话、用户明确指定 harness、已验证能力与权限、结构化输出要求、操作风险”选择 harness。不得仅根据未做本地对照验证的模型能力传言，把某类任务固定分配给 DeepSeek/MiMo 或 Antigravity。现有 Claude Code 内 DeepSeek/MiMo 的公平轮换不变。

Antigravity 不参与该公平轮换。它完成 P2 双平台验证后有明确的默认角色：对**无历史会话、无敏感内容、只读且明确需要独立审查、第二方案、反方意见或风险清单**的新任务，选择 Antigravity 的独立 reviewer role；项目延续、受控 execute、需要 CC Switch profile/plugin/MCP 或一般的新项目协作，默认选择 Claude Code 的 project collaborator role。高风险 execute 默认由 Claude Code 执行、Antigravity 至多做一次只读 critique。用户明确指定 harness 始终优先。

每次 Agent 迭代（包含文档、配置、脚本、测试和迁移）都必须同时考虑 macOS 与 Windows。变更记录必须列出两端影响、验证证据或明确的不受影响理由；不得把 POSIX 路径、Bash、权限、launcher、认证或 session 行为默认套用到 Windows。

## 7. 文档治理与版本策略

产品需求、技术方案、实施计划和测试用例是**持续更新的主文档**：始终描述当前有效规则，不为每一次优化复制完整版本。每次实质变更同时更新受影响主文档，并在 `docs/迭代记录.md` 记录日期、动机、影响、验证和迁移事项。调用/harness 相关变更还必须链接或复核 [headless CLI 参考基线](headless-cli-references/README.md)，并记录 macOS 与 Windows 的影响和验证。

对存在明确取舍、需要长期追溯或可能被推翻的决定，新增短决策记录 `docs/决策记录/DEC-YYYYMMDD-<slug>.md`，包含状态、上下文、决策、备选方案、影响的主文档和废止关系。Git commit/tag 提供逐字历史；只有发布里程碑、对外接口/schema 变更或重大基线冻结时才给主文档标注版本号。

一次有明确问题、讨论基线和后续实施的优化，不直接作为顶层 `docs/` 文件保存，而是使用 `docs/专题/YYYY-MM-DD-<slug>/`。专题入口必须声明：固定讨论基线（提交、版本或其他可定位证据）、状态、关联 DEC、受影响主文档、实施/测试证据和替代或归档关系。专题方案记录当时的假设与分期；当前有效规则仍只写入四份主文档。
